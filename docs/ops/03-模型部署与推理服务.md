## 1. 终裁声明：单轨 Ollama，本地即生产

**裁决**（用户，2026-09-26）：推理服务**单轨 Ollama**，不建 vLLM/云推理第二现役渠道（旧稿双轨提案否决）；**本地机即生产环境**（RTX 4060 8GB，Windows 宿主，Ollama 原生免 WSL2——沿用旧稿 14 §9.1 结论）。

理由（2026-09-26 终裁依据）：

1. **GPU 现实**：RTX 4060 8GB 只够单并发中小模型常驻（§2.3 显存预算）；vLLM 的吞吐优势以 ≥24GB 显存与高并发为前提，本机兑现不了；
2. **单人运维**：vLLM 需 Linux GPU 服务器、CUDA/驱动版本管理、独立容器编排，运维成本超出单人承受；Ollama 单二进制、模型分发内建、Windows 原生；
3. **lite/full 档一致性**：[锚点 §3.2](../architecture/01-总体架构与分层.md) 部署分档要求默认档个人/小团队跑得起来——单机 Ollama 是 lite 档的自然组成，不引入「部署档位 × 推理渠道」的二维矩阵。

**约束继承**（旧稿 14 §9.3 跨阶段统一约束中栈无关项，2026-09-26 沿用）：

1. 接口子集：业务代码只经 ModelGateway 统一接口（chat/embed/tools/`response_format`）；Ollama 私有参数（如 `format`）只允许出现在 L7 `infra/llm` 适配层，违者评审打回；
2. 结构化输出走 OpenAI 兼容 `response_format: json_schema`（LiteLLM 统一透传）；
3. 切换校准：任何模型/渠道切换前后以同一评测集双跑，核心指标（抽取 F1 / 工具调用成功率）劣化 >2% 阻断切换、回退旧渠道（与 [08 篇 §7.2](../architecture/08-横切关注点与工程规范.md) 变更强制回归同源）。

## 2. 部署形态与模型清单

### 2.1 形态：Ollama 服务经 L7 ModelGateway 统一接入

| 项 | 基线（来源：旧稿 14 §9.1 配置基线，2026-09-26 沿用） |
| ---- | ---- |
| 服务 | Ollama 常驻（Windows 宿主原生进程，开机自启/看门狗——deploy 资产见 §6 待办），**不并入五存储 Compose**（GPU 归宿主管） |
| 端口 | 11434（默认），仅绑定本机/内网；LiteLLM `api_base` 指向 |
| 模型目录 | `OLLAMA_MODELS` 显式规划磁盘目录（§5.1），不散落用户默认目录 |
| 并发 | `OLLAMA_NUM_PARALLEL=1`（8GB 省显存） |

| 加速 | flash attention 开启 |
| 健康检查 | `GET /api/tags` 探活（巡检脚本消费；与 LiteLLM `/health` 联动纳入 [02-运维手册](./02-运维手册.md) 巡检项） |
| 接入 | ModelGateway 渠道 provider `ollama/<model>`（07 §2）；预算/限流/成本落库口径不变（§5.3） |

### 2.3 显存预算（8 GB，来源：旧稿 14 §9.1）

上表合计 ~6.2 GB，与桌面占用相抵即打满；两条纪律：**训练与推理互斥**（QLoRA 训练期间停 Ollama，§3）；不追加第四个常驻模型——新增角色须先挤掉旧角色或换更小量化。

### 2.4 冷启动与预热（2026-09-26 痛点优化）

> 痛点来源：[11-链路排查与模块痛点台账](../architecture/11-链路排查与模块痛点台账.md) 全模块普查「模型×Ollama」**P0**——模型随请求换入换出显存，首请求分钟级延迟，直接击穿 TTFT SLO。对策三件：**常驻**（该在的不换出）、**预热**（换出/重启后自动恢复）、**预算**（换入可见可控）。

**keep_alive 常驻策略**（Ollama 请求级参数，由 L7 `infra/llm` 适配层按角色统一注入，业务代码与 ModelGateway 接口无感）：

| 角色 | keep_alive | 策略 |
| ---- | ---- | ---- |
| 对话主模型（Qwen3-8B） | `-1`（常驻不换出） | 对话链 TTFT 的直接依赖；除训练互斥（§3）外不参与换出 |
| 嵌入（bge-m3） | `-1`（常驻不换出） | 检索/记忆链高频且仅 ~1.2 GB，常驻代价最低 |
| 抽取 / 批量 | 按需换入 | 抽取现复用主模型（§2.2），天然常驻；批量任务（大批量嵌入重算、评测双跑、未来独立批量模型）以短 keep_alive（建议 5m）换入，用完自动让位 |

**显存账本（8 GB，常驻 1+1 的量化占用估算——均为估算值，随 §6「模型清单冻结」实测冻结）**：

| 项 | 估算占用 | 说明 |
| ---- | ---- | ---- |
| Qwen3-8B Q4_K_M 权重（常驻） | ~5 GB | §2.2 |
| KV-cache（num_ctx 16K、单并发、q8_0） | ~1.1 GB | 建议 `OLLAMA_KV_CACHE_TYPE=q8_0`（显存约减半、质量损失可忽略）；fp16 KV 约 ~2.2 GB，常驻 1+1 装不下 |
| bge-m3（常驻） | ~1.2 GB | §2.2 |
| 系统 / 桌面预留 | ~1 GB | 不可侵占（与 §3 训练互斥同源） |
| **模型侧合计** | **~7.3 GB，贴顶** | **常驻 1+1 是 8 GB 的极限配置**：换入任何批量模型必然触发主模型换出；新增常驻须先挤掉旧角色或换更小量化（§2.3 纪律） |

**启动预热探针**：Ollama 探活通过（`GET /api/tags`，§2.1）后，自动对每个常驻模型各跑**一次空请求**（chat：`max_tokens=1`；embed：单条短文本），把分钟级权重加载挪到服务启动窗口，首个用户请求不付冷启动成本；探针纳入 [02-运维手册](./02-运维手册.md) 巡检项，预热失败 = 常驻模型不可用，按 P1 告警。

**指标与 TTFT SLO 关联**：`model_cold_start_seconds`（histogram，标签 model）= 从请求抵达至模型就绪（首 token 返回）的耗时，由 L7 适配层上报（§5.2）；与 [07 篇 §6](../architecture/07-基础层设计.md) 的 `chat_ttft_seconds{tenant,model}`（SSE 编码器首 token 时刻）同看板联防——常驻生效时冷启动 ≈0，**非零尖峰即一次换入事件**，直接抬高 TTFT 最坏分位；TTFT SLO 达标的前提是本指标日曲线清零。

**换入换出预算**：每次按需换入 = 一次显存挤压 + 一次延迟尖峰。设**换入次数/日**预算（建议初值 ≤10 次/日，实测冻结），超限告警 P2（沿 [08 篇 §6](../architecture/08-横切关注点与工程规范.md) 分级）——语义是常驻清单与实际负载错配，须回填 §2.2 模型清单重裁决（挤掉旧角色或换更小量化），不允许长期靠换入换出硬撑 TTFT SLO。

### 2.5 num_ctx 强制注入与并发准入（2026-09-26 痛点优化，P1）

- **num_ctx 静默截断防线**：Ollama 默认 num_ctx=4k，超限静默丢最旧消息（会话宪法/工具定义丢失→工具循环失控）。规则：ModelPort 出站一律显式注入 `num_ctx`（默认 ≥16K，随上下文预算表联动），响应侧核对 prompt_eval_count 接近 num_ctx 即告警 `model_ctx_truncated_total`——禁止依赖 Ollama 默认值；
- **并发准入**：Ollama 默认串行（NUM_PARALLEL=1），提并发以 batch/显存为代价。v1 裁决：**保持串行 + 模型并发信号量（Agent/03 §3）做准入与排队**，对话路径预留（已在冷启停账本内）；NUM_PARALLEL>1 的吞吐收益随 PoC 实测再开（开则同步下调 num_ctx 预算防 OOM）。

## 3. 微调闭环（LLaMA-Factory QLoRA → GGUF → Ollama）

（来源：旧稿 14 §9.4 阶段一闭环，2026-09-26 终裁沿用为**唯一**微调上线通道——旧稿阶段二 vLLM LoRA 热挂载通道随 §4 终裁作废）

链路：**QLoRA 训练（LLaMA-Factory）→ merge → 导出 GGUF 量化 → Ollama Modelfile 导入（新模型名）→ ModelGateway 切流**。

- **切流与回滚**：切流 = `deploy/config/llm.yaml` 渠道指向新模型名（先过 §1 约束 3 评测双跑）；**回滚 = 指回基座模型名，秒级**，无状态迁移；
- **权威产物**（旧稿 §9.3 约束 2 沿用）：merge 后 **BF16 safetensors 为唯一权威产物**（归档 MinIO `model-artifacts` 桶，版本化、可追溯）；GGUF 是部署衍生品，随用随转、不入权威库；
- **节奏**：merge→GGUF→import 为偶发操作，单轮约十几分钟，可接受（旧稿实测口径）。

8GB 显存约束表（来源：旧稿 14 §9.4 资源边界，2026-09-26 细化）：

| 项 | 约束（建议值，首次训练实测冻结） |
| ---- | ---- |
| 微调对象 | ≤4B 级 QLoRA；7B+ 租卡（AutoDL 4090 级，按小时计费）或暂缓 |
| 序列长度 | ≤2K（建议 512~1024，超长样本截断） |
| batch | per-device 1~2 + 梯度累积凑等效 batch |
| 量化 | QLoRA nf4 |
| LoRA 秩 | 8~16 |
| 推理互斥 | 训练期间停 Ollama 释放显存；训完先起 Ollama 再验收 |
| 显存水位 | 训练峰值 ≤7 GB，留 ~1 GB 给系统/桌面 |

## 4. 与旧稿 vLLM 提案对账（专节）

（对账对象：旧稿 [架构设计/14](../架构设计/14-部署与运维.md) §9.2/§9.4 阶段二，2026-09-26 对账）

**旧稿主张**：两阶段路线——阶段一 Ollama（单机开发/试用）→ 阶段二 Linux GPU 服务器 vLLM；触发条件三条（≥24GB 显存 GPU 到位 / 并发会话 >5 / 微调高频迭代需 LoRA 热挂载）。

**vLLM 的真实优点（承认，不抹杀）**：PagedAttention + 连续批处理（高并发吞吐）、prefix cache（Agent 多轮循环省重复 KV）、guided json（结构化保障）、`--enable-lora` 适配器热挂载（训完即测免转换）。

**不采纳理由（2026-09-26 终裁）**：

1. **单轨终裁**：用户已否决双轨——双轨意味着两套渠道配置、两份评测基线、两条运维路径，单人团队养不起；任一时刻只有一条现役渠道（旧稿 §9 铁律本身也这么要求）；
2. **GPU 现实**：RTX 4060 8GB 撑不起 vLLM 的吞吐优势（其优势区间 = 高并发 + 大 KV 池）；单机单人低并发下 Ollama 足够，vLLM 的调度与常驻 KV 开销反而吃显存；
3. **运维复杂度**：vLLM 无 Windows 原生支持（需 Linux GPU 服务器 + CUDA 栈管理），与「本地即生产」直接冲突；
4. **档位一致性**：见 §1 理由 3。

**未来触发条件（再评估，登记为待办而非承诺，§6）**——满足其一重开评估（沿用旧稿 §9.2 触发条件收敛）：

- 并发会话持续 ≥5（指标口径待定义，§6）；
- 更换 ≥24GB 显存 GPU（4090/A10 级）；
- 微调进入高频迭代、GGUF 转换时延成为瓶颈（需要 LoRA 热挂载）。

届时**切换零代码**承诺不变（§1 约束继承）：只改 llm.yaml 渠道指向（LiteLLM `hosted_vllm/` 前缀），业务代码零改动；重开评估须先过 §1 约束 3 的评测双跑。

## 5. 运维要点

### 5.1 模型下载与磁盘管理

- 模型统一落 `OLLAMA_MODELS` 规划目录；下载默认官方 registry，国内网络配镜像/代理；
- 磁盘水位：模型目录所在盘 free <20% 告警（P2，[02-运维手册](./02-运维手册.md) 分级框架）；旧量化版本用 `ollama rm` 定期清理，仅保留现役 + 上一版（回滚位）；
- 微调产物（BF16 safetensors）归档 MinIO 后本地副本即删，不占模型目录。

### 5.2 显存与监控指标（接 07 篇 §6 指标清单）

- 沿用 07 §6 LLM 指标：`llm_calls_total`、`llm_tokens_total`、`llm_latency_seconds`（标签 model/profile）——本地渠道照常上报，口径不变；
- 本机新增建议指标（接入 OTel，登记 02-运维手册联动）：GPU 显存占用率、GPU 利用率、推理 OOM/排队计数（数据源 nvidia-smi / DCGM）、`model_cold_start_seconds` 与换入次数/日（口径、TTFT SLO 关联与告警预算见 §2.4——2026-09-26 痛点优化）；
- 告警分级（沿 [08 篇 §6](../architecture/08-横切关注点与工程规范.md) 框架）：显存打满致推理失败 = P1；磁盘水位 / 旧模型堆积 = P2。

### 5.3 成本记账

- **本地推理电力/折旧不计 token 成本**：`llm_calls` 成本字段对 `ollama/*` 渠道记 0 并带 `channel=local` 标签——08 §6 月度成本归因报表可区分本地/云端；
- **云端溢出才计费**：仅 fallback 到云 API（07 §2.2 fallback 策略）时按 USD 实计；预算/限流（07 §2.3）对本地渠道放宽、对云端渠道从严。

### 5.1 LiteLLM 网关加固（2026-09-26 P2）

锁精确版本+依赖哈希（曾发生 PyPI 供应链投毒窃凭据，条件允许走私有源镜像）；Proxy 进程内存上限+低峰周期性重启窗口（官方已知长驻泄漏）；spend 日志走本平台 llm_calls 批量通道（07 篇）而非其自带逐请求写。
