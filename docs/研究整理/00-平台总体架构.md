# 00 - ontology-rsi-harness 平台总体架构

> 状态：v0.1 草案 | 依据：`docs/研究资料/` 三份资料 + 产业调研（详见 01~06 分篇）
>
> 本文回答三个问题：平台是什么、由哪些核心服务构成、它们如何协作成闭环。

---

## 1. 平台定位

**ontology-rsi-harness** 是一个**以本体为语义基座的智能体（Agent）平台**：

- 向上：托管多种 **agent 工具**（nanobot、openclaw、hermes agent、claude、piagent 等），为它们提供统一的模型接入、记忆、知识、工具与插件能力；
- 向中间：以 **graphrag-ontology 知识库 + 本体推理核心** 为平台的中枢语义层，为 Agent 提供"可信业务上下文"与"可校验的逻辑约束"，抑制幻觉；
- 向下：以 **MCP 协议** 为能力出口，把本体定义的对象、规则、动作暴露为可执行的业务算子，打通业务系统，形成"决策→执行→回流"的行动闭环。

这与《本体智能研究报告（AIIA 1.0）》的判断一致：本体智能定位为**大模型与业务系统之间的语义中间层**——向上为大模型提供精准、可解释的业务知识，向下将决策意图转化为可在业务系统中执行的标准化动作。

### 1.1 平台要解决的三个问题（来自行业共识）

| 痛点 | 传统方案 | 本平台方案 |
| ---- | ---- | ---- |
| 业务执行与数据分析割裂 | BI 只出结论，落不了地 | 本体行动层：事件驱动，回写业务 API |
| 业务规则"隐形化" | 规则硬编码在代码里 | 规则成为本体一等公民（公理/约束逻辑） |
| 专家经验"游离化" | 经验随人走 | 经验沉淀为本体规则 + 多层记忆 |

### 1.2 设计原则（来自《本地建模》笔记，必须写进平台宪法）

1. **OB2 建模法**：对象（Object，第一性）— 行为（Behavior，改变对象状态）— 规则（Rule，不变式、独立定义）；关注相对稳定的对象与关系，而非易变的流程。
2. **事件驱动逆向闭环**：`事件 → 规则 → 行为 → 回写API → 更新数据`。
3. **推理分级**：确定性强的高频逻辑交给规则引擎；低频复杂语义判断才交给大模型——**别把确定的事丢给大模型做概率推理**。
4. **最小够用、宁简勿繁**：先划业务边界 → 再定方案档次（词汇表/轻量图谱/重型本体）→ 最后选工具；警惕过度设计。
5. **机器粗加工 + 人工终审**：LLM 产出的是候选本体，术语唯一、规则人工把关、实例合规，全程可追溯。

## 2. 总体架构

```mermaid
flowchart TB
    subgraph 接入层
        UI[Web / API / 消息渠道]
        EXT[外部 Agent 系统]
    end

    subgraph 平台核心服务
        direction TB
        AGENT[Agent 服务<br/>模型协议 + Agent 协议<br/>托管 agent 工具运行时]
        KB[知识库服务<br/>graphrag-ontology<br/>GraphRAG 检索]
        ONTO[本体核心<br/>本体建模 / 存储 / 推理引擎<br/>OWL-RDF-SHACL]
        MEM[记忆服务<br/>多层记忆<br/>会话-用户-组织-知识]
        MCP[MCP 网关<br/>平台能力出口 + 外部 MCP 接入]
        PLUGIN[插件服务<br/>插件市场 / 插件管理]
        TOOL[工具集服务<br/>工具注册 / 管理 / 分发]
    end

    subgraph agent 工具（被平台托管）
        T1[nanobot]
        T2[openclaw]
        T3[hermes agent]
        T4[claude]
        T5[piagent]
    end

    subgraph 资源层
        LLM[模型服务<br/>多模型统一接入]
        BIZ[业务系统<br/>ERP / MES / CRM ...]
        EXT_MCP[外部 MCP Server]
        DATA[(图数据库 / 向量库 / 关系库)]
    end

    UI --> AGENT
    EXT <-.-> MCP
    T1 & T2 & T3 & T4 & T5 --> AGENT
    AGENT --> LLM
    AGENT --> MEM
    AGENT --> KB
    KB --> ONTO
    AGENT --> MCP
    PLUGIN --> TOOL
    AGENT --> PLUGIN
    MCP --> BIZ
    MCP <-.-> EXT_MCP
    ONTO --> DATA
    MEM --> DATA
```

### 2.1 与《本体智能研究报告》三层架构的映射

| 报告三层 | 平台承载服务 | 说明 |
| ---- | ---- | ---- |
| **语义层**（是什么） | 本体核心 + 知识库（graphrag-ontology） | 对象/属性/关系/规则约束四要素，统一业务语义 |
| **决策层**（做什么） | Agent 服务 + 本体推理 + 记忆 | 逻辑推理、一致性校验、触发条件；规则引擎 + LLM 双轨（推理分级） |
| **行动层**（怎么做） | MCP 网关 + 工具集 + 插件 | API 接口、动作编排、权限控制；执行结果回流更新本体 |

### 2.2 核心闭环（平台的灵魂）

```
知识感知 → 推理决策 → 执行反馈 → 知识更新
   ↑___________________________________|
```

一次完整链路：Agent 接收任务 → 从 graphrag-ontology 检索业务上下文 → 本体推理核心做规则校验/隐含推理（确定逻辑走规则引擎）→ 决策经 MCP 网关调用业务系统接口执行 → 执行结果与数据变化回流，更新本体实例与多层记忆。

## 4. 产业参照（为何这样设计）

《本体智能研究报告》对 Palantir / 微软 / Google 三条路线的对比，四点共性趋势直接支撑本平台设计：

1. **轻形式化的工程化路线是共识**——本体价值锚点从纯逻辑推理转向"Agent 的可信上下文供给"，平台不做重学术本体，形式化程度按需（三档方案：词汇表/轻量图谱/重型本体）。
2. **本体从静态知识表示演进为可执行语义层**——规则与动作纳入本体（对应 OB2 的行为/规则、GB/T 48000.3 的"行动/约束逻辑"实体类型、Palantir 的动力部分）。
3. **MCP 正成为本体对外服务的事实互操作接口**——Palantir Ontology MCP、微软 Fabric IQ、Google 全线默认 MCP。平台的 MCP 网关是战略性组件，不是可选项。
4. **人工建模与 AI 自动生成将收敛于人机协同**——对应平台知识库服务的"机器粗加工 + 人工终审"流水线。

行业落地参照：电力配电网停电分析（本体思维链）、电信宽带退单（准确率 65%→90%+）、空客 A350 供应链（Palantir）、银行反洗钱合规。共性成功要素：**围绕具体业务痛点、本体建模紧密贴合行业、形成分析→执行闭环**。

## 5. 落地路线（六阶段工程流程）

《本体智能研究报告》六阶段，作为平台的参考交付流程：

| 阶段 | 关键工作 | 平台对应能力 |
| ---- | ---- | ---- |
| 1. 领域理解与需求分析 | 专家访谈、定义能力问题（Competency Questions）、明确数据源 | 建模工作台（人工） |
| 2. 本体建模 | 语言选择（OWL 2 DL / RDFS）、模块化、命名规范 | 本体核心·建模（符合 GB/T 48000.3） |
| 3. 本体实例化 | LLM 少样本抽取实体/关系 + 本体约束下实体链接 | 知识库·抽取流水线 |
| 4. 验证与质量评估 | 语法/一致性验证、能力问题验证、专家评审 | 本体核心·推理校验 + SHACL |
| 5. 部署与集成 | 版本管理、存储选型、推理服务封装、**经 MCP 暴露为 Agent 工具** | MCP 网关 + 工具集 |
| 6. 持续维护与演化 | 数据变化监控、执行结果回流、概念漂移检测 | 记忆服务 + 知识库巡检 |

**风险与治理**（报告 + 建模笔记共识）：专家资源稀缺（核心专家+外延网络、本体工程师做"翻译者"）、概念定义权博弈（需高层推动与变更评审机制）、知识漂移（双负责人、周期巡检、版本回滚）。
