# 03 - 知识库（graphrag-ontology）与本体核心

> 状态：v0.1 草案 | 依据：GB/T 48000.3-2026、《本体智能研究报告 1.0》、《本地建模》笔记
>
> 知识库服务解决"知识从哪来、怎么检索"；本体核心解决"知识长什么样、怎么推理"。二者合起来是平台的语义层。

---

## 1. 服务边界

```
文档/数据/专家经验                          业务问题
     │                                         ↑
     ▼                                         │
┌─────────────────────────────────────────────────────────┐
│ 知识库服务 graphrag-ontology                              │
│  文档预处理 → LLM 批量抽取 → 术语对齐 → 校验 → 人工归档      │
│  GraphRAG 检索：实体/关系图谱 + 社区摘要 + 本体约束          │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────┐
│ 本体核心                                                  │
│  本体建模（GB/T 48000.3）· OWL/RDF 存储 · SHACL 约束       │
│  推理服务：描述逻辑推理 + 规则引擎 + LLM 协同（推理分级）      │
└─────────────────────────────────────────────────────────┘
```

- **本体核心**管理 TBox（术语层/模式层：类、属性、公理、规则）；
- **知识库服务**管理 ABox（实例层：从文档和数据抽取的实体/关系实例）并对外提供检索（GraphRAG）。
- 对 Agent 而言：检索走知识库（给上下文），校验/推导走本体核心（给约束），二者都经 MCP/工具集暴露。

## 2. 本体核心

### 2.1 建模方法论：OB2 + 三步法 + 六步实战

**OB2 核心方法**（《本地建模》）：

| 要素 | 核心问题 | 原则 |
| ---- | ---- | ---- |
| 对象 Object | 存在什么？ | 对象是第一性的 |
| 行为 Behavior | 能做什么？ | 行为改变对象状态 |
| 规则 Rule | 什么条件必须成立？ | 规则是不变式，独立定义 |

通过**事件**串联形成逆向闭环：`事件 → 规则 → 行为 → 回写API → 更新数据`。

**建模三步法**（顺序不能错）：
1. 划业务边界（是术语不统一？还是要复杂推理？）
2. 定方案档次：

| 档次 | 适用场景 | 核心能力 |
| ---- | ---- | ---- |
| 轻量词汇表 | 跨部门术语不统一 | 统一名词定义 |
| 轻量知识图谱 | 定义实体与基础关系 | 实体关系网 |
| 重型本体 | 高风险强推理场景 | 复杂逻辑约束与自动推理 |

3. 选工具建模（Protégé / rdflib / 图数据库…）。

**六步实战**：业务专家访谈 → 提取核心概念（层级）→ 定义属性关系（方向/基数）→ 添加业务公理（本体区别于普通图谱的核心）→ 模型评审 → 推理测试（小批量数据验证后迭代）。

**四大陷阱**：概念与实例混淆、不加约束（退化成普通图谱）、过度设计、脱离业务。

### 2.2 国标落地：GB/T 48000.3-2026 要点

《标准数字化 第3部分：本体建模要求》，2026-01-28 发布、2026-08-01 实施。平台本体核心应将其作为**建模规范基线**（即使业务不是"标准"领域，其模式层设计——实体类型/属性/公理/扩展原则——是可直接套用的工程范式）。

**本体三要素**：实体类型 + 属性（数据属性/对象属性）+ 公理。

**形式化要求**：
- 采用 W3C 本体语言：XML、RDF/RDFS、OWL；
- 序列化格式：Turtle、JSON-LD；
- 支持 **SHACL 约束验证**（如标准编号格式校验）；
- 命名：`IRI = XML命名空间 + 本地标识符`，如 `http://example.org/standard-ontology#Standard`；命名空间用本体管理机构域名。

**核心实体类型**（国标定义的 15 类，面向"标准"领域，可作为平台行业本体的参考模板）：

| 类别 | 实体类型 | 说明 |
| ---- | ---- | ---- |
| 根节点 | 标准实体 Standard | 唯一标识的标准化文件实体，含编号/名称/日期/状态/约束类型等 |
| 元数据 | 标准化对象、相关方（机构/个人）、领域类别（ICS/CCS） | 描述主题、参与角色、分类 |
| 结构 | 要素（规范性/资料性）、层次（章/条/段/列项） | 标准文本结构 |
| 技术内容 | 术语、信息单元（条款/附加信息）、信息单元表述形式（条文/图/表/公式/附录/引用/提示）、对象、特性（描述型/能力型/约束型）、约束逻辑、行动、外部约束（法规/专利/文献/公共数据库） | 知识的语义单元 |
| 流程 | 制定程序（预备→立项→起草→征求意见→技术审查→批准发布→出版→复审→废止） | 全生命周期 |
| 可选扩展 | 版本、文件编号 | 版本树/差异分析场景 |

**34 个核心对象属性**（节选关键）：adopts/replaces/cites/references/hasPart（标准间关系）、issuedBy/draftedBy/administeredBy（责任关系）、hasStructuralElement/hasClause/hasSubClause（层次）、defines/usesTerm（术语）、involvesObject/specifiesCharacteristic/hasCharacteristic（对象与特性）、imposesConstraint/constrainsObject/constrainsCharacteristic（约束）、describesAction（行动）、hasDevelopmentStage（流程）。

**公理与规则**（第8章，推理服务的约束来源）：
- 实体类型规则：互斥类型定义不相交（如规范性要素 vs 资料性要素）；需唯一标识的类型定义全局唯一 ID；
- 属性规则：唯一值约束（标准编号）、日期有效性（实施日期≥发布日期）、枚举约束（标准状态）、取值约束（强制/推荐）；
- 关系规则：函数性约束（每个标准只有一个发布机构）、版本替代规则（废止必须指向替代标准）、层次约束（章可含多条；无标题条不可含子条）、引用关系区分。

**元数据描述项**（附录A）：实体类型 8 项（IRI/Name/Label/Definition/属性集/SubclassOf/HasSubclass/EquivalentClass）；属性 10 项（含 Domain/Range/TypeOfTerms）。平台建模工作台的"本体元数据表单"直接按此设计。

**扩展原则**（第9章）：扩展用新命名空间、不与已有定义矛盾、不修改核心定义、行业本体模块化扩展。

**实例化示例**（附录D）：GB/T 31486-2024 电池标准 → Turtle 三元组（标准实体→层次→条款→对象→特性→约束逻辑→行动），可直接作为平台知识库的抽取目标格式。

### 2.3 推理服务设计（推理分级原则）

```
                ┌─ 确定性强、高频 ──→ 规则引擎（Drools类）/ SHACL 校验     毫秒级、确定性
推理分级 ──────┤
                └─ 低频、复杂语义 ──→ LLM 概率推理（受本体上下文约束）
```

| 推理类型 | 引擎 | 用途 |
| ---- | ---- | ---- |
| 一致性检验、分类推理（TBox） | OWL 推理机（HermiT/ELK/pellet 类，或 rdflib+pySHACL 轻量方案） | 检测逻辑矛盾、冗余公理、意外结论 |
| 约束验证（ABox） | SHACL | 实例合规校验（格式、枚举、区间、基数） |
| 隐含关系推导 | 描述逻辑推理 / 图遍历 | 由规则推出未显式记录的结论（如审批路径） |
| 语义判断 | LLM + 本体上下文注入 | 低频复杂场景；输出仍需过规则校验 |

**与大模型结合的三档集成**（按需选择，避免过度设计）：

| 档次 | 作用 | 适用场景 |
| ---- | ---- | ---- |
| 轻量级 | 本体作为 RAG 的过滤器，解决概念混淆 | 知识库问答助手 |
| 中量级 | 本体作为 Agent 的动作与规则底座，限定行为边界 | 医疗、金融等高风险合规场景 |
| 重量级 | 本体推理引擎与 LLM 混合推理 | 强规则、复杂链式推理 |

（"基于本体的思维链"可参考电力案例：把复杂分析标准化为"获取对象→提取数据→计算指标"固定流程，配套双盲检测校验查询意图。）

### 2.4 版本管理与治理（对抗知识漂移）

- **双负责人机制**：业务负责人 + 知识工程师共同维护；
- **变更管控**：申请 → 评审 → 发布 → 回滚；核心概念变动需业务影响评估；
- **周期巡检**：知识一致性、推理准确率、异常关系检测、三元组冲突检测；
- **版本管理**：每次修改存档，支持对比与回滚（对齐国标可选"版本"类设计）；
- **使用数据驱动迭代**：监控本体调用频次与决策支撑效果，形成"建设—应用—反馈—优化"闭环。

## 3. 知识库服务：graphrag-ontology

### 3.1 知识抽取流水线（机器粗加工 + 人工终审）

**七步流水线**：

```
文档预处理 → 环境配置 → 批量抽取 → 术语对齐 → 一致性校验 → 约束校验 → 人工归档
```

**四大国标底线**（防幻觉，必须内置到流水线的门禁里）：
1. **候选非成品**：LLM 生成的是候选本体/实例，必须人工审核后入库；
2. **术语唯一性**：一个概念只有一个名字（对齐国标"相同实体类型的近义词不应表示为多个实体类型"）；
3. **规则人工把关**：动作、公理、约束规则最终由人工确认固化；
4. **实例合规性**：所有实例必须通过本体结构约束（SHACL）校验。

**文档预处理**（统一输入格式）：

| 文档类型 | 预处理方法 |
| ---- | ---- |
| Word / 纯文本 | 转 Markdown，按章节分片 |
| 可复制 PDF | 提取纯文本，剔除冗余 |
| 扫描件 / 图片 | OCR 提取（关键术语人工复核） |
| 复杂流程图 | 多模态大模型直接解析 |
| Excel / 表格 | 拆分合并单元格→标准表格，跨表关联人工梳理 |

**分类型抽取策略**：

| 知识类型 | 抽取目标 | 提示词要点 |
| ---- | ---- | ---- |
| 文本知识型 | 概念、属性、对象、关系 | 固定输出结构 + 附原文定义，禁止凭空创造 |
| 数据型 | 实例、属性、值域约束 | 针对表格输出实例属性和值域 |
| 时序流程型 | 动作、前置条件、状态流转、互斥规则 | 生成动作控制属性（为 Agent 提供素材） |
| 图片/流程图 | 关键实体与关系 | 多模态提示词，禁止脑补 |

**工具链参考**：

| 工具 | 用途 |
| ---- | ---- |
| ONTO GPT | 本体抽取，快速上手 |
| Protégé | 本体编辑、可视化、推理机校验（人工终审工具） |
| Tesseract / TADOC | OCR |
| Python rdflib + pySHACL | 批量本体处理、约束校验 |
| LangChain / LlamaIndex | 自定义抽取流水线编排 |

**避坑**：永远不要完全信任 LLM 自动生成的公理和规则；结果必须可追溯（保留原文出处指针）；控制分片长度与并发量。

### 3.2 GraphRAG 检索

- **机制**（[microsoft/graphrag](https://github.com/microsoft/graphrag)）：LLM 实体/关系抽取 → 构建知识图谱 → 层次化 Leiden 社区检测 → 每个社区生成 LLM 摘要（community report，多粒度层级）。检索模式：
  - **Global Search**：面向"整个语料库的主题/总结"类问题，对预生成社区摘要做 map-reduce，不遍历原始图，token 高效；
  - **Local Search**：面向具体实体问题，取相关实体、关系、关联文本单元与社区报告，结合向量索引；
  - **DRIFT Search**：全局+局部混合（先社区摘要后实体展开），质量/成本折中；
  - **LazyGraphRAG**：延迟索引——查询时才做图遍历，索引成本约等于向量 RAG（约为完整 GraphRAG 索引的 0.1%），成本敏感场景可借鉴。
- **本体增强**（graphrag-ontology 的差异点）：抽取时用本体做 schema 约束（实体类型映射、术语对齐，参考 deepsense.ai 的 ontology-driven GraphRAG 实践与 Neo4j `neo4j-graphrag` 本体引导抽取），检索时用本体做查询扩展与过滤，回答时附图谱路径作为证据链——缓解纯向量 RAG 的概念混淆与幻觉。注意：**Neo4j 本身不是推理机**（经 n10s 插件可导入 RDF/OWL 到属性图，但无 OWL 推理引擎），一致性校验/复杂推理需外挂 GraphDB / Apache Jena Fuseki，推理结果物化回属性图。
- **与平台其他服务的关系**：为 Agent 服务提供上下文检索工具（经 MCP/工具集暴露）；抽取产物落本体核心做校验后入库；社区摘要与本体推理结果可注入多层记忆的知识级（04 篇 L4）。

### 3.3 存储选型

| 组件 | 候选 | 说明 |
| ---- | ---- | ---- |
| 图存储 | Neo4j / NebulaGraph / TuGraph / Memgraph | Neo4j：GraphRAG/Agent 生态集成最多（neo4j-graphrag、LangChain、LlamaIndex、Graphiti 默认支持）+ n10s 本体插件，中小规模首选；NebulaGraph/TuGraph：千亿边级分布式、多租户大并发（TuGraph 兼具信创生态）；Memgraph：内存优先，实时流式场景（Graphiti 支持的后端之一） |
| RDF 三元组/推理 | rdflib / Apache Jena Fuseki / GraphDB | TBox 管理与描述逻辑推理（外挂于属性图） |
| 向量库 | Milvus / pgvector / Qdrant | 文本切片、社区摘要的语义检索（混合检索） |
| 关系库 | PostgreSQL | 文档元数据、审核工单、版本记录 |

**推荐组合**：起步~中等规模用 **Neo4j（含 n10s 导入本体）+ 本体引导抽取 + pgvector/Milvus 混合检索**；规模化（百亿边/多租户）再迁 NebulaGraph/TuGraph；需严格 OWL 推理时外挂 GraphDB/Jena Fuseki。国标提示：小规模场景可 PostgreSQL + rdflib 起步，避免一上来堆全套存储。License 细节（Neo4j 社区版 GPLv3 等）采购前需复核。
