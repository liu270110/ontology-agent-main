## 1. 总则

### 1.1 测试左移：用例是开发的验收合同

平台零代码起步，测试体系先于代码设计——**任何模块动工之前，其验收用例（02 篇对应域）必须先行评审通过**。用例即开发与设计之间的合同：合同没签，代码不算开工。

- **可追溯**：每条用例必须追溯到上游设计文档的具体条目（不变式行 / 降级分支 / 端点 / 错误码 / 事件映射），不接受"测个大概"；
- **同步演进**：上游条目变更时用例同步修订，新不变式 / 新端点 / 新事件必须同步增用例（维护规则见 [README](./README.md)）；
- **宪法的测试映射**：三条设计宪法各有一类专属用例，不得合并进功能用例顺手测——候选非成品 → 候选隔离用例（TC-KB-009）；推理分级 → golden 基准用例（TC-EVAL-006）；全程可追溯 → 审计断言用例（TC-RBAC-012、TC-MCP-002 等）；
- **契约先行**：OpenAPI 是前后端唯一契约（锚点 §3.3、08 篇 §8.2），schema 快照即契约测试的对照组。

测试左移的标准作业流（与锚点 §6.6 文档规范一致）：

1. 设计文档定稿（含不变式表/路由清单/事件映射表）并评审通过；
2. 按上游条目起草用例（02 篇对应域），ID 只增不改；
3. 用例评审通过 = 验收合同签订，方可开工编码；
4. 编码与单测同 PR 提交，CI 相关阶段全绿；
5. 缺陷按 §5 定级处置，P0/P1 修复附回归用例；
6. 里程碑出口按 §7 最小集逐行验收。

### 1.2 测试金字塔

依赖严格单向分层（锚点 §2）决定了测试成本自下而上递增，金字塔形状如下：

| 层级（自底向上） | 对象 | 起步数量占比 | 单套时长预算 |
| ---- | ---- | ---- | ---- |
| L4 领域单测 | 聚合不变式、状态机、领域事件、领域服务/端口接口 | 约 70%（最多） | 毫秒级/用例，全套 < 3min |
| L6 仓储与语义集成 | 仓储实现、UoW、迁移、五存储客户端、流水线、本体制品 | 约 15% | 分钟级/套 |
| API 契约 | REST 端点、SSE 帧、错误码、DTO 校验 | 约 10% | 分钟级/套 |
| E2E | 关键闭环冒烟（对话全链路、建模工作台） | 约 5%（少而精） | 小时级/套 |

纪律：**禁止把 E2E 当回归主力**——E2E 只守锚点 §3.5 的关键闭环；任何能在下层复现的失败都必须在下层有用例。

形态依据：08 篇 §8.2 金字塔四层（领域单测/仓储集成/契约/E2E），本文在其上补语义 golden 与性能/安全两个专项层——专项层不改变"下多上少"的形态。

反模式（评审打回项）：

- 用 E2E 补下层没写的用例（慢且不稳定，治标不治本）；
- mock 掉被测对象的核心协作方再断言"协作成功"（自说自话）；
- 为凑覆盖率写无断言用例（跑过即绿）；
- 不变式只放集成层测（04§2.1 的迁移/形状类必须在 L4 穷举，竞态类才下到 L6）。

### 1.3 覆盖率门槛

| 范围 | 门槛 | 依据/说明 |
| ---- | ---- | ---- |
| L4 `services/domain/` | ≥ 90% | 04 篇 §7 为权威；08 篇 §8.1 已统一为 ≥90%（2026-09-26 裁决取更严者——2026-09-26 评审修复G：原「08 篇写 80% 属下限」的滞后口径作废） |
| L3 `services/business/` | ≥ 80% | 编排分支与降级路径必须显式覆盖 |
| L5 `services/semantic/` | ≥ 80% | 推理路由、SHACL、版本治理 |
| L6 `services/data/` | ≥ 75% | 仓储实现分支 |
| 整体 | ≥ 75% 起步 | M2 后按实测收紧至 80%；覆盖率随 CI diff 报告呈现 |

工具：`coverage.py`（pytest-cov）+ 分层 `fail_under` 配置。**覆盖率是门禁不是目标**：不变式覆盖优先于行覆盖——04 篇 §7 要求 §2 每条不变式至少合法 + 非法各一个用例，此要求不因行覆盖率达标而豁免。

说明：

- 分层门槛固化在 `pyproject.toml` coverage 配置，CI 机器可复现，不接受本地口头达标；
- 行覆盖与不变式覆盖双轨报告：不变式覆盖清单（04 篇 §2 逐条 → 用例 ID）随 02 篇维护，评审时人工核对。

## 2. 分层测试设计

总表（各层展开见下）：

| # | 层 | 测什么 | 怎么测 | 工具 | 运行时机 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| ① | 领域单测 | 不变式、状态机、事件纪律、分层契约 | 纯内存、无 IO、不 mock 存储（04 篇 §7：领域层无桩可打） | pytest、pytest-cov、import-linter | 每次提交（含 pre-commit） |
| ② | 数据层集成 | 仓储实现、UoW、并发唯一索引、迁移、五存储客户端 | testcontainers 起真实实例；Neo4j/Milvus 打 full 档专属标记 | testcontainers-python、pytest 标记 | 每次提交（lite 子集）+ nightly（full 全量） |
| ③ | 语义层 golden 基准 | 推理正确性 30 例、round-trip、diff、检索 golden QA | 固定基准集 + 指标断言 | pytest 参数化 + 评估 harness | CI 常驻（小集）+ nightly 全量 + 变更触发回归 |
| ④ | API 契约 | 端点、SSE 帧、错误码、DTO、分页、幂等 | OpenAPI 为契约；单请求断言 + 属性测试 | FastAPI TestClient、Schemathesis、schema 快照 | 每次提交 |
| ⑤ | E2E | 对话全链路 SSE、建模工作台关键流 | 真实浏览器驱动全栈 | Playwright | nightly + 里程碑出口 + 发布前 |
| ⑥ | 性能与容量 | SSE 多副本、回写吞吐、推理 SLA | 负载模型 + 阈值断言 | k6（SSE/HTTP）、locust（场景） | nightly / 里程碑出口 |
| ⑦ | 安全 | 注入、越权、SSRF、工具投毒 | OWASP 快查 + 静态扫描 + 渗透用例 | semgrep、pip-audit、插件包验签扫描 | 静态每次提交；动态周期 + 发布前 |

层间分工三原则（用例落层评审依据）：

- **下移优先**：新用例先问能否在更下层测——能在单测测的不进集成，能在集成测的不进契约，能在契约测的不进 E2E；
- **一处一测**：同一断言只在一层出现（SSE 帧格式在契约层断言，E2E 只断言业务闭环）；
- **故障注入对齐降级矩阵**：08 篇 §5 每行降级至少一个故障注入用例（08§10 待办"注入测试纳入 CI 冒烟"的落地）。

### 2.1 ① 领域单测（L4）

- 范围：`services/domain/tests/test_<聚合名>.py`（04 篇 §7 文件组织）；**100% 纯单测**，不连任何存储、不 mock 存储客户端；
- 不变式即测试：04 篇 §2 总表逐条映射为 TC-DOM 用例（02 篇 §2），合法 + 非法各一；
- 状态机穷举：session / task+run / review / plugin 四个状态机全部非法迁移参数化断言（04 篇 §3、§8）；
- 架构契约并入本层门禁：import-linter 禁止 domain import 框架与上层（04 篇 §1），违规即构建失败。

不做清单：不测 HTTP 细节（归契约层）、不连存储（归集成层）、不 mock 框架与存储对象（领域层无桩可打，04§7）。

### 2.2 ② 数据层集成（L6）

- PG / Redis / MinIO 用 testcontainers 每次起真实例：覆盖仓储实现、UoW 事务、Alembic 迁移、审计只追加、outbox 同写同滚；
- **Neo4j / Milvus 用例打 `@pytest.mark.full` 专属标记，只在 full 档环境执行**（nightly）；lite 档同时维护等效降级实现的用例（PG 递归 CTE 图遍历、pgvector 向量检索——锚点 §3.2 部署分档：功能验收标准不降，性能档不同）；
- 并发/唯一类不变式在本层验证（04 篇 §2.1 裁决）：如 session 双活跃 Run 由 PG 部分唯一索引拒绝（TC-DOM-001）；
- 集成测试每用例自建租户与数据、结束自清理（08 篇 §8.2 纪律）；
- Alembic 迁移用例：upgrade/downgrade 往返与第一批表结构断言（M1 随迁移交付）；
- 审计只追加断言：对 audit_logs 的 UPDATE/DELETE 一律被拒（08 篇 §3）。

### 2.3 ③ 语义层 golden 基准（L5）

- **本体推理基准 30 例 CI 常驻**（本体 §10）：TBox 一致性矛盾 10 例（检出率 100%）、SHACL 违规 10 例（检出 100%、误报 0）、隐含关系推导 10 例（与人工标注一致 ≥ 99%）；另含 round-trip 图同构与 diff 正确性断言；
- **检索 golden QA 集**（08 篇 §7.1）：按检索模式（local / global / drift）分层构建"问题—金标答案—金标证据"，种子场景 = 电力停电分析；指标为引用率、答案忠实度、检索命中率；
- 性质区别：golden 用例断言的是**指标对基线的 delta**而非单值 pass/fail，与 §6 评估体系联动；基准集版本化（08 篇 §7.3），跨次可比；
- SLA 类断言（如推理耗时）在锚点 PoC ① 冻结数字前**不进 CI 硬阈值**（本体 §5.1 裁决）；
- golden 集文件组织：`tests/golden/ontology/`（.ttl 基准图 + 预期报告 JSON），基准例只增不改（与用例 ID 纪律一致）。

### 2.4 ④ API 契约（L2）

- OpenAPI schema 为唯一契约：八个 routers 全端点必须出现在 schema 且标注所需 scope（02 篇 §4、§8）；
- TestClient 单请求断言：错误体四字段同构（02 篇 §7）、DTO `extra="forbid"`、分页、幂等键双落；
- Schemathesis 属性测试：按 OpenAPI 自动生成请求，断言无 5xx、响应符合 schema；请求量限额配置防打爆测试环境；
- schema 快照变更必须在 PR 中显式确认（08 篇 §8.2：防接口悄悄漂移），快照 diff 未确认即 CI 失败（TC-API-009）；
- SSE 帧级契约在本层用 ASGI 级客户端断言（帧格式、心跳、主干波事件集），跨副本场景留给 ⑥ 压测与 E2E；
- 属性测试请求量限额：Schemathesis 配置 max_examples 与过滤规则，防打爆测试环境。

### 2.5 ⑤ E2E（L1→L7 全栈）

- 范围锚定两条关键流：**对话全链路 SSE**（发消息 → 检索 → 生成 → 工具 → 回写 → RUN_FINISHED，M3 起）与**建模工作台关键流**（建模 → 抽取 → 检索 → 对话 → 回写，锚点 §3.5 链路，M4 起）；
- 工具 Playwright 驱动 Vue3 前端，compose 全栈起（08 篇 §8.2）；浏览器对未知 SSE 事件名一律忽略的前向兼容行为也在此验证（02 篇 §5）；
- E2E 用例少而精（金字塔 §1.2），每条必须对应一个里程碑出口条件；
- 前端组件测试与视觉回归策略随 docs/frontend 设计稿定稿后细化（登记 §8 待办）。

### 2.6 ⑥ 性能与容量

- **SSE 多副本压测 = M3 出口条件**（锚点 §7、02 篇 §8）：双副本、同一会话双连接分落两副本，Last-Event-ID 跨副本重连不重不漏；
- 压测后冻结建议值：心跳 15s、回放窗 10min/1000 条、停机排空 30s（02 篇 §2/§5 均为"压测后冻结"项）；
- 回写吞吐（M4）：幂等投递 + 对账任务容量；推理吞吐随 PoC ① 冻结值补充（本体 §11）；
- 工具 k6（SSE 长连接 / HTTP）+ locust（多角色场景），阈值断言进 nightly 报告，里程碑出口时人工确认；
- 压测结论回填机制：冻结值更新走 PR 修改本文与 02 篇对应用例，附压测报告链接留痕。

### 2.7 ⑦ 安全测试

- OWASP 快查清单逐项：**注入**（SQL 全走 ORM、Cypher 参数绑定、SPARQL 入口白名单——`/ontology/query` 的 `sparql` 参数）、**越权**（IDOR / 跨租户抽样，TC-RBAC-009/011）、**SSRF on MCP**（外部 MCP Server 注册 URL 禁内网地址、重定向校验）、**工具投毒**（插件包验签失败不得进审核——04 篇 §2 plugin；依赖静态扫描）；
- 授权红线专项：MCP `annotations` 不作授权依据（08 篇 §2.3 安全红线，TC-MCP-001）；
- 静态扫描（semgrep 自定义规则 + pip-audit）每次提交；动态渗透用例周期执行 + 发布前必跑；
- 密钥纪律：凭据进 `infra/security` 托管、测试与审计中不落明文（08 篇 §3 脱敏规则）；
- 高风险动作参数快照信封加密落库断言（08 篇 §3）；安全用例与用例域映射：注入→TC-API/TC-ONTO-014、越权与租户→TC-RBAC、SSRF/投毒→TC-MCP。

## 3. 测试数据管理

- **fixtures 工厂**：一律 factory 模式构造（08 篇 §8.2 纪律），禁静态 JSON 大快照——数据模型演进时工厂改一处、快照改一片；
- **种子数据 = 电力场景样例集**：锚点 §7 钦定首个行业场景为电力配电网停电分析，种子本体（20~50 类 OB2 精简模型）+ 样例数据集是 M2 出口条件；种子集同时是 golden QA（08 篇 §7.1）与抽取金标集（≥500 条，与 PoC ② 共用）的数据底座，**一套种子三处复用，不允许第二套种子**；
- **测试租户隔离**：集成测试每用例自建租户与数据、结束自清理；测试租户命名带 `test-` 前缀便于巡检兜底清理；
- **绝不连生产**：测试配置强制断言（环境守卫：检测到生产 DSN/密钥指纹即 fail-fast 拒跑）；生产数据禁止导入测试环境（08 篇 §3 审计红线）；
- **数据版本**：种子集随本体版本演进（M2 种子本体为出口条件之一），golden 集与种子集版本号绑定，升级种子集必须同步跑全量 golden（防基准漂移）；
- **敏感数据**：测试中不得出现真实用户数据与真实凭据；测试密钥独立于生产托管，走 `.env.test` 分层配置。

## 4. 测试环境与 CI 阶段

- **本地 lite 档**（PG + Redis + MinIO，锚点 §3.2 部署分档）承载 CI 主干——保证个人/小团队提交即测；
- **full 档**（+ Neo4j + Milvus）跑 nightly，覆盖 `@pytest.mark.full` 用例、E2E 与性能压测；

CI 阶段设计（顺序对齐 08 篇 §8.1 门禁顺序，任何阶段失败即阻断合并）：

| 阶段 | 内容 | 触发 | 时长预算 |
| ---- | ---- | ---- | ---- |
| lint | ruff（lint+format）、mypy（domain/semantic strict）、import-linter 分层契约 | 每次推送 | < 2min |
| unit | `pytest tests -m "not integration"`（L4 单测 + 纯策略） | 每次推送 | < 3min |
| integration-lite | testcontainers：PG/Redis/MinIO 集成 + lite 档等效降级用例 | 每次推送 | < 10min |
| contract | TestClient 断言 + Schemathesis + schema 快照比对 | 每次推送 | < 5min |
| eval-regression | golden QA / 基准对比（08 篇 §7.2） | **仅触及模型/本体版本/检索参数/提示词的 PR** | < 15min |
| nightly-full | full 档集成（Neo4j/Milvus）+ E2E + 性能 + 安全动态 | 每日 | < 60min |

- nightly 失败视为 P1 缺陷：24h 内修复或回滚触发变更（§5 SLA）；
- 每阶段产出 JUnit 报告与覆盖率 diff 附于 PR，评审可查。

环境矩阵：

| 环境 | 档位 | 用途 | 数据 |
| ---- | ---- | ---- | ---- |
| 本地开发 | lite（PG+Redis+MinIO） | 日常开发与自测 | 工厂自造 |
| CI 主干 | testcontainers lite | 每次推送五阶段（除 eval-regression 按需） | 每用例自建自清 |
| nightly | compose full（五存储） | full 集成 + E2E + 性能 + 安全动态 | 种子集快照 |
| 压测环境 | full + 多副本网关 | SSE 双副本 / 回写吞吐 / 推理基准 | 种子集放大 |
- 前端构建与测试阶段随 M5 前端全量接入（锚点 §7 待办：CI 加前端构建阶段）。

## 5. 缺陷管理

严重级定义与响应 SLA：

| 级别 | 定义（示例） | 响应 SLA | 修复 SLA |
| ---- | ---- | ---- | ---- |
| P0 | 主链路不可用；数据损坏/丢失；安全红线突破（跨租户泄漏、候选未过审直接生效、无凭证进 succeeded） | 立即 | 24h 内修复或回滚 |
| P1 | 关键功能降级且无绕行（SSE 重连丢事件、unknown 盲目重试、巡检误报重建） | 4h | 3 个工作日 |
| P2 | 有绕行路径的功能缺陷、体验问题 | 1 个工作日 | 本迭代内 |
| P3 | 轻微：文案、日志噪音、非关键告警误报 | 排期 | 排期处理 |

**缺陷 → 回归用例转化规则**：

1. 每个 P0/P1 缺陷的修复 PR 必须附带新增回归用例（进 02 篇对应域，ID 只增不改）；
2. 缺陷复盘时检查同类不变式/降级分支是否有用例缺口，有则补齐（防"修一处漏一片"）；
3. P2/P3 缺陷在迭代复盘时批量评估是否转化，不强制。

缺陷记录必填字段：用例 ID（或显式标注"无对应用例"）、复现步骤、环境与版本、trace_id、严重级、日志/截图附件；"无对应用例"的缺陷复盘时必须评估新增用例。

复盘节奏：P0/P1 修复后 48h 内复盘（根因 + 用例缺口 + 同类不变式是否受损）；每迭代汇总 P2/P3。

放行豁免：出口评审可对非红线用例申请一次性豁免（记录原因 + 补绿时限，最长跨一个里程碑）；红线类不可豁免——P0 级用例、候选隔离（TC-KB-009）、安全红线（TC-RBAC-009/011、TC-MCP-001）、回写契约（TC-MCP-005~009）。

## 6. 评估与测试的关系

- **golden QA 是"语义正确性"测试的扩展**（08 篇 §7）：普通用例断言 pass/fail；语义用例断言指标对基线的 delta——检索质量、任务成功率、抽取精确率没有二值答案，只有"比基线好还是差"；
- **变更强制回归 = 合并门禁**（08 篇 §7.2）：模型 / 本体版本 / 检索参数 / 提示词任何变更，合并前必须跑评估集对比基线；回归作为 CI 独立阶段追加在 §4 门禁顺序之后，仅触及上述变更的 PR 触发；
- 初始阈值：**主指标退化 -2% 即阻断合并**（建议值，实测后冻结——与锚点"数字实测后冻结"裁决一致）；
- 评估 harness 与 pytest 共用 §3 的 fixtures 工厂与种子集，杜绝"测试一套数据、评估另一套数据"的漂移。

普通测试与评估的分工对照：

| 维度 | 传统测试 | 评估（golden） |
| ---- | ---- | ---- |
| 判定 | 单值 pass/fail | 指标对基线 delta |
| 触发 | 每次提交 | 仅触及四类变更的 PR |
| 数据 | 工厂构造 | 版本化 golden 集 |
| 失败动作 | 修代码至绿 | 阻断合并 + 指标归因 |
