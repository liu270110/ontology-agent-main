## 1. 评审结论

### 1.1 全体专家共识的强项（不动摇）

1. **控制面/数据面分离 + 判据由 harness 求值**（§3 规律 4/5）——全篇最耐模型迭代的主张，四位技术专家一致认可；
2. **任务状态外置 ABox + 漂移检测**（§6.2-4）——对 context rot 与崩溃恢复是真解，对 DSec"单一事实源"的移植准确；

4. **能力层四通道 + 八扩展点**（§7.3/7.4）——增量边界诚实，未翻任何已定稿 ADR。

## 2. 五位专家研讨纪要（浓缩）

### 2.1 本体工程专家

**总体**：OB2→harness 四面的映射方向正确，行动类先行是真增量；但 §6 运行时的核心卖点停在"断言"层面——门禁底座与存储 ADR 之间有缝，任务本体表达不了自家要求的 DAG。

**最重的问题**：① [P0] 门禁"SPARQL ASK/SHACL 毫秒级"与 ABox 在 Neo4j 脱节（n10s 无 SPARQL 端点、pySHACL 十万级三元组即秒~十秒、HermiT 为秒~分钟级）；② [P0] Step 只有线性"序"、无 `dependsOn`、无 Plan 类，撑不起"合法 DAG"与并行派发；③ [P1] "计划图整体过 SHACL"可表达性过 claim——DAG 无环、跨步产消匹配等超出 SHACL 邻域局部性，需三层校验；④ [P0→表述] §1.2 的"循环/上下文/工具/校验四面"与 §5.1 的"感知/行动/验证/触发四面"两套四元组对不上（主编注：已修）；⑤ [P1] 任务本体缺时间/角色/失败补偿/审计元类，判据含"SLA 达标"却没有期限属性。

**关键提问**：SPARQL ASK 到底打哪个存储？Step 依赖边与 Plan 类何时进任务本体 v0.1？误路由（语义步被规则执行）如何兜底？

### 2.2 系统与运行时专家

**总体**：方向正确且克制；但 §6 是"伪代码级正确、工程级欠账"。单步延迟由 LLM 往返主导，Neo4j 单写不是瓶颈——真正的未验证项在门禁求值与跨库一致性。

**最重的问题**：① [P0] 门禁求值基座缺失（同 2.1①，并给出解法：**任务级 RDF 投影**——grounding 时投影相关子图为会话内 rdflib 图、写透回 Neo4j、门禁打在投影上，PoC 实测）；② [P0] 每步写回（ABox+AG-UI+审计+Outbox）跨库无原子性协议，PG UoW 不覆盖 Neo4j，且 PG 的 Task 领域对象与 ABox 的 task:Task **双主未裁决**；③ [P1] KV-cache 自相矛盾：§3 引 Manus"遮蔽而非增删"，§6.3 却按行动类每步换 schema，实际前缀命中仅宪法+TBox 约 15%；④ [P1] 并行步 TOCTOU（互斥行动类可同时过门禁）；⑤ [P1] "重连续跑"覆盖度不足（工具原始结果不在 ABox、非幂等动作重放会重复副作用）。

**关键提问**：ABox 写成功而 PG 审计失败时以哪边为准、谁重放补偿？PG Task 与 ABox task:Task 谁是主本？

### 2.3 LLM 工程与上下文专家

**总体**：verifier-in-the-loop 与状态外置是少数可依赖的确定性杠杆；但文档把"本体可校验"过度外推成"决策可压缩"——执行通道没有自由形式出口，最关键的参数（首轮计划通过率、修复上限、N、预算占比）全部悬空。当前形态"更像信仰声明+结构对账，离可实现差一次 PoC"。

**最重的问题**：① [P0] **决策空间过约束**：LLM 只能"选行动类+填参数"，无代码/脚本行动类——而本文自引的全部 harness（Claude Code/pi/SWE-agent/DSec）核心动作都是代码执行；每个长尾操作都要先建行动类，本体工程反成瓶颈，这是把 harness 做成"高级表单引擎"的路径；② [P0] **规划与循环自相矛盾**：规划时 Step 已绑定行动类，循环又说模型"选行动类"——只能选计划内的则偏离即校验白做，可改选则"计划可校验才有资格执行"失效；③ [P0] **装载即判决**：术语对齐/实体链接错误 → 判据全错且被"确定性"地执行到底；④ [P1] 首轮计划合法通过率无实测（结构化输出只保 JSON 语法，τ-bench Retail 头部模型约 86%，pass^k 更低），且 SHACL 查结构合法不查目标一致；⑤ [P1] Turtle 序列化 token 密度数倍于自然语言（KGQA 研究一致显示口头化更优），10% 预算装不下行业 TBox，"摘要怎么算"未定义。

**关键提问**：Step 被证明不可行时重规划的触发/范围/再校验是什么？判据由对齐产物生成——它错了谁发现？

### 2.4 安全与治理专家

**总体**：存在一个结构性自相矛盾——**完成判据是对 ABox 的查询，而 ABox 每步由 agent 自己写回**："确定性裁判"裁决的是被告自己写的笔录。DSec §6.4 案例库被引为参照，但其核心教训（agent 会钻营验证器）没有转化为任何防线；§6.5 失败模式表缺席注入、判据操纵、供应链投毒，全文没有威胁模型章节。

**最重的问题**：① [P0] **判据自证**：SHACL 只约束形状不约束真假，`task:hasStatus "succeeded"` 是完全合法的三元组；且 §6.2-6 顺序是"判据通过 → 才回流业务 API"，真实回执发生在判据求值之后；② [P0] **校验器可被能力包私有化**：恒真的 gates.pre 或恒过的 gates.post 即构成完整攻击链，"无语义标注不上架"只管"标了什么"、无机制验证标注与实现相符；③ [P1] 不可信输入边界只覆盖工具输出——GraphRAG 证据、记忆召回、L1 技能（纯提示词即可诱导判据自证）、错误报告回流全部裸奔；平台 MCP 出口的 `memory.write` 若与任务 ABox 同图，外部 agent 可绕开循环直写 task 命名空间；④ [P1] 审批在环语义缺失（waiting_approval 预算是否计时、批准是否绑定参数哈希、批准疲劳）；⑤ [P1] 多租户边界在可插拔组件上失守（context.providers/memory.policies 无 tenant scoping 契约）。

**关键提问**：判据引用的每个事实如何设计性地保证 100% 来自外部系统回执？能力包 gates.post 恒通过时，还有哪道独立于它的防线？任取一条 ABox 三元组能否回答"这是模型、规则还是人写的"？

### 2.5 行业落地专家

**总体**：工程完成度很高的"平台灵魂"设计，但回答的全是"怎么建"，几乎没回答"谁买单、多久见效、凭什么赢"。技术形态不构成壁垒（MCP 是三巨头共识），真正的潜在壁垒（本体资产沉淀、记忆反哺飞轮、行业规则库）只是 ADR 条目没被当作商业资产经营。**最大悬空项：全程没有一个具名的试点行业和客户。**

**九大痛点**（详见归档全文）：① 冷启动——第一个客户凭什么是"建模投资者"而不是等模板的后来者；② 首个行业试点至今悬空——没有客户名的里程碑凭什么算验收；③ ROI 时间线——M5 才有完整闭环，前 12+ 个月价值真空；④ 竞争位——Fabric IQ 下一个版本内置你全部四个扩展点时客户凭什么留下；⑤ 对"微调+RAG+Dify"1/10 成本方案的证明义务未产品化；⑥ 组织阻力只有流程件没有激励件——业务负责人的述职报告上哪一行写本体质量；⑦ 交付人才——本体工程师人天数敢写进报价单吗；⑧ **信创是一票否决项**——Neo4j/Milvus/MinIO 清一色国际栈，电力/金融/政务采购全卡目录；⑨ 知识中台失败潮——闭环依赖"agent 拿核心系统写权限"，客户安全部门第一反应是否决。

**三条行动建议**：两周内锁定试点行业，M2-M5 验收标准改写为"具名试点客户用它解决了什么"；把"证据链问答+CQ 回归评测"从 M3 拆出为首个可独立计费产品，配对照实验记分卡；壁垒叙事从架构切换到资产（记忆反哺本体的数据飞轮 + L2 行业能力包）。
