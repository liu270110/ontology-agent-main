## 1. 专家 A —— 平台架构师（15 年，单体→微服务演进/架构评审）

### 优势确认
1. 各层职责/禁令成表，且给出 import-linter、中间件顺序断言等可执行检查点，分层不只是口号。
2. 「候选非成品+人工终审」与推理分级写进横切宪法，是 LLM 平台少见的合规自觉。
3. 03 篇降级路径写到失败分支级（检索/LLM/校验三条），天然可测。
4. 对自身缺陷（sevices 拼写、双路线冲突）诚实登记并定改名时点。

### 批判点

**[P0] L3/L4 边界规则不可执行，编排器注定长成规则泥球**
- 证据：03 §3 步骤表「降级纯向量继续」「违例剔除后继续」「循环上限 5 轮」全是策略判断，与 03 §1「编排禁写业务规则」、锚点「业务层不含业务规则本身」直接矛盾。
- 行业痛点：DDD 落地头号死因即应用服务变业务泥球、领域层贫血化；规则不能静态检查就等于没规则。
- 修正：改 03 §1/§3——重试/降级/预算类策略明确归 L3 并以可注入 Policy 对象表达，不变式归 L4；删「禁 if」式表述，换成 import-linter/评审清单可断言的条款。

**[P0] 微服务演进只有口号：无拆分触发条件，关键接口也不具备拆分形态**
- 证据：锚点 §1、sevices/README 称「Agent/语义/MCP 网关优先拆出」，但无触发指标与拆分序；SSE 回放绑进程内 Redis Stream（02 篇自认多副本未解），CapabilityProvider 是进程内注册表（锚点 §3.4）——最该先拆的两处恰是耦合最重的。
- 行业痛点：模块化单体失败首因是「模块边界=函数调用边界」，真拆时事件流与能力注册全部重造。
- 修正：锚点 §7 补拆分触发条件表（故障隔离/独立发布节奏/资源画像）；Outbox 事件与 Capability 协议按可跨进程设计（带版本、可换远程发现）。

**[P1] SSE 长连接叠加七层中间件全压 L2，网关必成容量与变更双瓶颈**
- 证据：02 篇中间件「定稿不可调换」；事件同步写 Stream、15s 心跳、30s 排空均在同进程；多副本方案挂起。
- 行业痛点：网关既持长连接又转发 token 流，内存与连接数先打满，会话粘性锁死水平扩容。
- 修正：SSE 推送统一从 Redis Stream 消费（副本无状态）；多副本问题升级为 M3 验收前置项。

**[P1] 起步即重型：Outbox、27 张表、15 个 SSE 事件、双负责人首日全上**
- 证据：03 篇 Outbox+relay+死信；06 篇 27 张核心表；02 篇 15 个事件；03 篇四眼原则。
- 行业痛点：Outbox 三件套（延迟监控/死信/幂等消费）缺一即退化为双写不一致，比不用更糟；表与事件全量前置拖垮 M0~M3。
- 修正：Outbox 推迟到出现真实外部消费者（M4），此前同事务写+进程内发布；SSE 首版砍到 8 个（TEXT/TOOL/RUN 主干）；06 篇的表按里程碑分期建。

**[P1] 文档治理是官僚定时炸弹：锚点先行+全仓 README 联动**
- 证据：architecture/README 四步变更流程；锚点要求每目录六段式 README spec（全仓 40+ 篇）。
- 行业痛点：迭代压力下「先改锚点再评审」必被绕过，文档漂移后锚点权威归零，比无锚点更糟。
- 修正：锚点只锁三类不变量（层名/依赖规则/顶层路径），其余下放分篇；六段式 README 随 PR 更新，M0 只验收 gateway/business 两份。

**[P2] 依赖倒置只做一半：对最不稳定的 L7 反而直连**
- 证据：锚点 §2 允许 BIZ→INF、SEM→INF 直调 LiteLLM/mcp_gateway，无 ModelPort/ToolPort；03 篇仅有 KnowledgeRetriever 经 L4 接口的孤例。
- 行业痛点：Ports & Adapters 的缺口恰开在最常更换的依赖（模型供应商、外部 MCP）上。
- 修正：锚点 §3.4 增第三处倒置（ModelPort/ToolPort，L7 实现），或规定 L3 一律经 L4 领域服务接口调 L7。

### 分歧预告
1. 推迟 Outbox 会遭审核/审计视角反对（候选门禁需强一致）；回应：门禁一致性靠 PG 同事务即可，Outbox 只服务跨模块通知。
2. SSE 事件砍半会遭前端视角反对（STATE_DELTA 支撑协作 UI）；AG-UI 蓝本已留语义，后补不改协议。
3. 不反对七层本身，只反对不可执行的规则；该团队无 DDD 演练经验，可检查性应优先于教义。

## 2. 专家 B —— DDD 领域建模专家（10 年，务实 DDD-lite）

### 优势确认
1. DDD-lite 定位清醒：应用服务归 L3、仓储接口倒置、Outbox 可靠事件，主动避开「DDD 大统一」幻灭陷阱。
2. 不变式随聚合逐条落地，且要求「每条不变式合法+非法单测」，可测试意识好。
3. 「LLM 产物候选非成品」门禁贯穿本体/文档/插件/记忆，四眼原则、双负责人成体系。
4. 事件纪律明确：过去式命名、frozen、载荷只含标识+摘要、结构只增不改。

### 批判点

**[P0] ontology 聚合「三重权威」悬空，聚合根不知道自己聚合什么**
- 证据：04 篇定 ontology 为聚合根，但自认「聚合内持有内存 Graph 还是仅存制品指针」未决；本体核心设计：权威制品在 MinIO、版本权威在 PG、编辑期权威在 rdflib 内存图。
- 行业痛点：事件风暴没做就定聚合清单的典型症状；若把 Class/Property/Axiom/Rule 纳入聚合即「聚合过大」，全量 save 不可行。
- 修正：聚合收缩为「当前版本指针 + changeset 状态」，TBox 内容以 (version, artifact_uri, checksum) 值对象引用；发布方法显式为 `publish(gate_report, 双负责人批准)`，由聚合断言后迁移状态，不让编排器代行裁决。

**[P0] Session/Task 聚合吞下消息流与事件流，两文档状态机互相矛盾**
- 证据：04 篇 session 内嵌 messages（只追加）、save 全量保存；Agenrt 篇 Task 内嵌 Run+TaskEvent 且「先落库后推送」；session 状态机（04 篇 vs Agenrt 篇）与 task 状态集两份文档不一致。
- 行业痛点：聚合过大 + 每次追加全量重写 O(n)；两份 v0.1 各写各的，等于聚合建模从未对齐。
- 修正：Message/TaskEvent 移出聚合或明确定义增量 append 持久化语义；以锚点名义裁决唯一的 session/task 状态机，04 篇改为引用。

**[P1] 「一个 UoW 只改一个聚合根」被自家示例当场违反**
- 证据：03 篇规则 vs 同篇步骤 8「UoW#2 消息落库+task 终态+outbox」——session 与 task 两个聚合同一事务。
- 行业痛点：教条规则逼实现者二选一：拆事务制造不一致，或默默违规；事务边界=一致性边界，不是聚合计数。
- 修正：改述为「一个 UoW=一个一致性边界」，附显式豁免清单并纳入 CI/评审检查项。

**[P1] 并发型不变式放错层，「100% 纯单测可测」主张不可达**
- 证据：「同一会话仅一个 running task」「同对象唯一 open 工单」「存在 running task 禁删 agent」均为并发约束，04 篇却主张零存储纯单测覆盖。
- 行业痛点：check-then-act 竞态住在 DB 隔离级别，聚合内存断言防不住并发创建。
- 修正：不变式表加「强制机制」列——迁移合法性归聚合方法（单测），唯一性归 PG 部分唯一索引/隔离级别（集成测试）。

**[P1] pydantic 做聚合的三处未设防**
- 证据：04 篇仅述「pydantic 用于模型定义与校验」；事件 frozen，聚合侧无任何配置约定。
- 行业痛点：默认 validate_assignment=False，直接改属性可绕过全部校验；pydantic 字段级结构相等冒充实体的标识相等；「校验」与「业务规则」混写是贫血化开端。
- 修正：聚合统一 model_config（validate_assignment、值对象 frozen），实体按 id 重写相等；validator 只管形状，不变式只写聚合方法。

**[P1] review 与 changeset 双审批权威，关键不变式反而缺漏**
- 证据：03 篇工单状态机与本体核心 changeset 状态机两套并存；不变式表漏掉「双负责人双批准」「message.seq 严格递增」「发布后 IRI 不可变」。
- 行业痛点：同一审批过程两个工件必然状态漂移；「同对象唯一 open 工单」是跨聚合约束，聚合不变式保不住。
- 修正：裁决 changeset 即 review 的被审对象（唯一流程头），补齐三条缺失不变式，跨聚合唯一性落 DB 约束。

**[P2] 仓储「同构九件套」+tenant 首参；领域服务端口错位**
- 证据：仓储缺 find_by_review_id、find_open_by_object 等事件消费方必需的查询；KnowledgeRetriever（唯一消费者是 L3 编排）被定义为 domain service，而真正的记忆域策略（沉淀阈值/升降层）悬空。
- 行业痛点：通用仓储综合征 + 泛化接口综合征（接口为分层而分层）。
- 修正：仓储按用例定制查询；tenant 作用域由 UoW 构造期绑定 per-tenant 仓储实例；检索端口移应用层，domain/services 只留参与业务裁决者。

**[P2] 事件清单与 Outbox 配合有缺口**
- 证据：OntologyGateRejected 不在事件表；document 中段状态无事件；outbox 表无 aggregate_type/aggregate_id 列，saga 消费方未声明。
- 行业痛点：只定义事件不定义消费者，最终一致性链条漏一环即静默丢数据。
- 修正：补「事件→消费者→失败语义/补偿」清单；outbox 加聚合标识列并声明按聚合的投递有序性。

### 分歧预告
1. 反对升级为完整 DDD/事件溯源：病根是文档间模型未对齐与聚合边界未裁决，不是 DDD-lite 深度不够。
2. Outbox relay 进程内轮询在多实例部署需选主/分布式锁，运维评审必挑战。
3. 接受「L5 语义层压在 L4 之下」，但前提是 domain/services 不再收纳纯检索/记忆端口，否则 L4 沦为端口垃圾抽屉。

## 3. 专家 C —— AI/LLM 平台技术专家（Agent 运行时/RAG/记忆生产化）

### 优势确认
1. 锚点 SSOT + 分层依赖禁令可用 import-linter 机械守护，非纸上分层。
2. 「候选非成品 + LLM 输出强制回灌 SHACL」是抗幻觉的正确底线。
3. 记忆全程不物理删除、可审计回放。
4. 检索 Playground 自带 trace 与消融验收，有评估意识雏形。

### 批判点

**[P0] GraphRAG 全家桶对零代码起步是过度工程，索引成本被严重低估**
- 证据：Otghrag 篇 Leiden+逐层 community report、三模式+RRF+rerank；LazyGraphRAG（索引成本约 0.1%）仅列待办。
- 行业痛点：微软 GraphRAG 实测索引一本书即数百万 token/数十美元/小时级，逐层摘要令成本随社区层级再放大，「索引费远超查询费」是社区常见弃坑原因。
- 建议：默认 LazyGraphRAG 路线，完整索引只对试点高价值子集开；M2 先交向量+BM25 基线，索引 token 预算标定提为 M2 出口条件。

**[P0] 人工终审无工时模型，万页规模不可运行**
- 证据：低置信全审、规则类 100% 审、置信≥0.9 抽检 10%；全文无工时估算。
- 行业痛点：万页≈2 万 chunk×每 chunk 约 10 候选≈20 万条，半数高置信仍余 10 万条×20 秒≈550 人时；LLM 自报置信度校准极差，此抽样等于静默放水。
- 建议：先以金标集标定校准曲线再定阈值；审核单元聚合为文档/实体批次；补「条/人时」吞吐模型并试点实测。

**[P0] L2 记忆引擎未 PoC 却写死全部设计**
- 证据：memorry 篇「mem0 或 Graphiti PoC 定」，但正文已固化两引擎各自机制；Graphiti 与 Neo4j 社区版兼容未确认。
- 行业痛点：两引擎存储拓扑迥异，换型即重写 schema 与召回；记忆系统典型「上线即静默失败」，冲突判定 90% 目标无金标不可验；L1 Redis+PG 仅归档任务单向搬运，失败即丢。
- 建议：PoC 提为 M2.5 出口条件，引擎耦合段标「待裁决」；先上 L1+PG 结构化 L2，L3 后置。

**[P1] rdflib+owlrl 的 SLA 与自留待办自相矛盾**
- 证据：05 篇承诺 owlrl P95≤5s、把「万三元组 SHACL P99≤100ms」写进 CI 门禁，却承认 1 万/10 万三元组基线未实测。
- 行业痛点：rdflib 纯 Python，owlrl 做 OWL2 RL 闭包在 10 万三元组常为分钟级且内存爆炸，语义网共识仅原型可用。
- 建议：SLA 改「实测后冻结」；定外挂 Jena/GraphDB 触发阈值；「路由器唯一入口」靠 import-linter+契约测试进 CI 强制。

**[P1] 五适配器全做，feed/collect_events 抽象泄漏**
- 证据：feed() 假设 mid-run 续投；五工具形态/事件通道各异；pi 桥接需长期自维护、claude 条款待法务。
- 行业痛点：适配器地狱——各 harness 恢复/审批/流式语义互不兼容，多数 CLI agent 不支持运行中注入，上游一升级适配器全线崩。
- 建议：M3 只做 builtin+claude 打样；feed 改可选能力协商；openclaw/hermes 走 A2A/MCP 标准接入替代自研。

**[P1] 全平台缺端到端评估基准**
- 证据：仅 kb 有组件级指标；chat_orchestrator 与 Agent 任务成功率零评估设计。
- 行业痛点：demo 到生产的头号死因即无 eval——换模型/调权重/本体升级后质量回归凭感觉，无从归因。
- 建议：新增评估设计：按三模式分层的 golden QA 集、Agent 任务成功率基准、变更强制回归。

**[P2] 关键数字缺依据：静态预算、60s 超时、1.8s 检索**
- 证据：token 预算表静态百分比；fallback「超时 60s」；四层并行召回无总延迟预算——L4 决定首 token。
- 建议：预算改绝对 token+窗口比例双约束；流式按 TTFT 3~5s 判超时；memory/context 定 p99≤800ms 并允许对话链路降级轻检索；fallback 候选须过 structured-output 兼容矩阵（抽取依赖 JsonSchema，换模型即翻车）。

### 分歧预告
1. M2 范围：「向量基线+LazyGraphRAG 先行、完整索引按试点 ROI 开」与现默认全家桶冲突，排期需重谈。
2. 底线 3「规则 100% 人工」规模化后必被绕过，建议现在设计规则模板+白名单自动通道（留痕），否则团队会私设后门。
3. L2 选型倾向 mem0（复用 PG/Milvus）+Graphiti 只做 L3，避免单个 Neo4j 图背 L3/L4 双语义。

## 4. 专家 D —— 行业落地与商业可行性批判（ToB 交付/知识工程）

### 优势确认
1. 语义层独立成层、「候选非成品」横切门禁，方向对齐 Palantir/Fabric IQ 共识。
2. 推理分级 + LLM 输出强制过确定性校验，是知识工程圈踩坑后的正确纪律。
3. 锚点文档机制与显式降级矩阵，工程素养高于多数个人项目。

### 批判点

**[P0] M0~M5 是 20 人团队的路标，单人+AI 必死在 M2**
- 证据：锚点 11 个模块、M5「前端全部页面」；五角色 RBAC、审计冷归档 3 年；仅 TBox 就 7 张表。
- 行业痛点：Dify 插件市场是数十人团队数年的生态成果；「个人造平台」公认死法是基建齐活、场景为零、无用户、弃坑。
- 修正：插件市场、A2A、沙箱、多租户、审计归档全部移出 MVP。wedge=单租户「建本体→抽取→检索→MCP 出口」一条线，3 个月可演示可收反馈。

**[P0] 冷启动成本全推给用户，第一个租户无解**
- 证据：研究整理 00 自认「专家稀缺、六阶段、概念定义权博弈需高层推动」；「首个行业本体试点」至今是待办——27 张表定稿了，首行业还悬着。
- 行业痛点：知识平台铁律——空工作台没人建本体；Palantir 靠驻场专家团队冷启动，个人项目没有。
- 修正：内置 1~2 个种子行业本体（就用研究整理 00 自己举的电力停电分析/电信宽带退单）+样例数据集，让用户「改模板」而非从零建模；同时以该场景反推数据模型与抽取策略优先级。

**[P1] 治理流程按 20 人知识团队设计，小租户被压死或绕过**
- 证据：双角色会签、双负责人+影响评估强制、底线 3「无自动通过通道」。
- 行业痛点：流程重于产出的知识库项目，用户最终用 Excel 绕过平台；治理必须随组织规模分级，全文档无「治理档位」设计。
- 修正：租户级治理分级——solo 档提交人即审批人+全审计留痕、高置信度自动通过；企业档才启双签四眼。

**[P1] 七大服务差异化与 commodity 资源错配**
- 证据：插件市场+沙箱、模型网关、多租户均与 Dify/Coze 正面撞车；真差异只有本体语义层+MCP 出口。
- 行业痛点：Dify 生态位已被占死，陪跑模块只烧单人带宽，不构成任何选用理由。
- 修正：80% 资源投 ontology_core、抽取流水线、MCP 回写契约；插件需求直接用 MCP stdio/外部 Server 替代。

**[P1] 最后一公里被画成最细的箭头**
- 证据：回写闭环被称「平台灵魂」，但 ERP/业务系统对接在全部文档中只剩 MCP 网关一个箭头；仅熔断，无回写幂等、对账、补偿、凭证设计。
- 行业痛点：Palantir 真护城河恰是 writeback 管道；企业集成占交付量 60% 以上，画成一行适配器等于自欺。
- 修正：把「业务适配器 SDK+回写契约」升为一等模块与文档，先打穿一个垂直连接器再谈平台。

**[P2] 五存储自托管的运维与许可证现实缺位**
- 证据：Neo4j 社区版+n10s；「规模化后按租户拆 database」——社区版不支持多 database 与 RBAC，多租户隔离方案踩许可证红线；Milvus 单机也拖 etcd/对象存储全家桶。
- 行业痛点：RagFlow 类项目用户流失多死于部署运维；自托管个人/小团队恰是本平台当前唯一现实用户群。
- 修正：默认 profile=PostgreSQL+pgvector（Neo4j 可选），Milvus 降为扩展 profile；文档明示 GPLv3 边界与云/本地双形态。

### 分歧预告
1. 坚持「先场景后平台」：M2 前拿不出行业 demo，一切架构精化暂停——不接受「平台先行、场景后补」。
2. 若只保一个模块，保 MCP 回写而非 GraphRAG：检索是 RagFlow 做烂的 commodity，回写才是差异化。
3. 治理分级是产品理念分歧：若坚持「门禁不可协商」，请在锚点写明目标客户是 20 人以上组织，明确放弃个人/小团队市场。
