## 1. 部署形态总览

### 1.1 双档位选型

部署分档的权威定义见[锚点 §3.2](../architecture/01-总体架构与分层.md)（2026-09-26 评审裁决），脚本与端口分工见 [deploy/README](../../deploy/README.md)：

| 档位 | 存储组合 | 语义层降级方式 | 适用场景 |
| ---- | ---- | ---- | ---- |
| **lite（默认）** | PostgreSQL（含 pgvector）+ Redis + MinIO | 图遍历 → PG 递归 CTE；向量检索 → pgvector | 开发、演示、个人/小团队自托管 |
| **full** | PG + Neo4j + Milvus + MinIO + Redis 全量 | 无降级 | 生产、规模化 |

- compose 拆分：`docker-compose.yml`（lite 基础）+ `docker-compose.full.yml`（full 覆盖叠加）；
- 功能验收标准两档一致（M0~M5 出口条件不因档位放宽）；
- 默认从 lite 起步，出现[容量/拆分触发条件](../architecture/01-总体架构与分层.md)（锚点 §7）或需要全量图谱/向量能力时再切 full。

### 1.2 许可证与商用注意

| 组件 | 许可证 | 部署侧注意 |
| ---- | ---- | ---- |
| Neo4j 社区版 | **GPLv3** | **不支持多 database 与 RBAC**：多租户只能属性级隔离（节点/关系带 `tenant_id` 属性 + 复合索引，[08 篇 §1](../architecture/08-横切关注点与工程规范.md)）；商用分发边界需法务确认。出现「多库隔离/企业特性」需求即触发企业版采购或迁 NebulaGraph/TuGraph 的评估点（锚点 §3.2/§7） |
| Milvus | Apache 2.0 | 单机版会拉起 etcd/对象存储等依赖，资源占用是 lite 档不默认含它的原因之一（deploy/README） |
| PostgreSQL / Redis / MinIO | 各自宽松许可 | 无额外部署限制 |

## 2. 环境要求

### 2.1 硬件建议（建议值，M0/M1 实测后冻结）

| 项目 | lite 档 | full 档 |
| ---- | ---- | ---- |
| CPU | 4 核 | 8 核起 |
| 内存 | 8 GB | 24 GB 起（Neo4j 页缓存 + Milvus 及其依赖组件占用大） |
| 磁盘 | 40 GB SSD | 200 GB 起 SSD |
| 网络 | 需可出网访问模型 API | 同左 |

### 2.2 软件前提

| 软件 | 版本 | 用途 |
| ---- | ---- | ---- |
| Docker Engine | ≥ 24 | 容器运行时 |
| Docker Compose | v2（`docker compose` 子命令） | 编排 |
| Git | 近期版本 | 拉取代码 |
| Python | ≥ 3.11（本地 3.13，锚点 §3.1） | CLI `onto` 安装运行 |

> 纪律（deploy/README）：compose 只做**开发与演示**环境；生产编排（K8s/Helm）在 M4 后按需引入。

### 2.3 端口清单

权威在 [deploy/README「服务与端口约定」](../../deploy/README.md)，本表为部署前防火墙/占用预检用：

| 服务 | 端口 | 说明 | 档位 |
| ---- | ---- | ---- | ---- |
| gateway (FastAPI) | 8000 | REST + SSE；OpenAPI 文档 `/docs` | 双档 |
| frontend | 5173 | Vite dev 端口；生产由 Nginx 托管静态资源并反代网关 | 双档 |
| postgres | 5432 | 业务权威库 | 双档 |
| redis | 6379 | 会话热数据/限流/队列 | 双档 |
| minio | 9000 (S3) / 9001 (Console) | 对象存储 | 双档 |
| neo4j | 7474 (HTTP) / 7687 (Bolt) | 图谱 + 本体物化（只读物化视图，权威在制品） | **full** |
| milvus | 19530（+9091 metrics） | 向量检索 | **full** |

## 3. 首次部署（lite 档）

### 3.0 部署前检查清单

- [ ] 硬件/软件满足 §2 要求；§2.3 端口全部空闲（预检命令见 §7 FAQ 第一行）；
- [ ] 模型渠道 API Key 已就绪（按 [07 篇 §2.4](../architecture/07-基础层设计.md) `deploy/config/llm.yaml` 的 profile 规划：balanced / reasoning / light / embedding）；
- [ ] 已决定部署档位（不确定就选 lite，后续可按 §4 增量切 full）；
- [ ] 备份目录/盘已规划（lite 档也建议从第一天起按[运维手册 §5](./02-运维手册.md) 做 PG 备份）。

### 3.1 获取代码

```bash
# Git Bash（Windows）：仓库放任意盘符，例如 E:
cd /e/learn-agnet-project && git clone <仓库地址> ontology-agent-mian

# Linux
cd /opt && git clone <仓库地址> ontology-agent-mian
```

### 3.2 配置 .env

```bash
# Git Bash（Windows）与 Linux 相同
cp deploy/.env.example deploy/.env    # .env 不入 git（07 篇 §7）
openssl rand -hex 32                  # 生成 JWT 密钥等敏感值
```

关键环境变量（统一 `OA_` 前缀，[07 篇 §7](../architecture/07-基础层设计.md)；**目标态命名，最终以 `deploy/.env.example` 为准**）：

| 变量 | 档位 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| `OA_DEPLOY_TIER` | 双档 | 是 | 部署档位开关 `lite` / `full`，语义层据此选择实现（PG 递归 CTE+pgvector 或 Neo4j+Milvus） |
| `OA_DATABASE_URL` | 双档 | 是 | PostgreSQL 连接串（业务权威库） |
| `OA_REDIS_URL` | 双档 | 是 | Redis 连接（会话热数据/限流/队列） |
| `OA_MINIO_ENDPOINT` | 双档 | 是 | 对象存储 endpoint（含端口） |
| `OA_MINIO_ACCESS_KEY` / `OA_MINIO_SECRET_KEY` | 双档 | 是 | MinIO 凭据 |
| `OA_JWT_SECRET` | 双档 | 是 | JWT 签名密钥；轮换流程见[运维手册 §7](./02-运维手册.md) |
| `OA_LLM_API_KEY`（按渠道分变量） | 双档 | 是 | 模型渠道 API Key（LiteLLM，profile 配置见 `deploy/config/llm.yaml`） |
| `OA_NEO4J_URI` / `OA_NEO4J_PASSWORD` | full | 是 | 图库连接 |
| `OA_MILVUS_URI` | full | 是 | 向量库连接 |
| `OA_LOG_LEVEL` | 双档 | 否 | 日志级别 |

密钥纪律：密钥一律不落代码库；本地开发 `.env`（gitignore）；生产经 secret 管理系统（Vault/云 KMS/部署平台注入）下发到进程环境（07 篇 §7）。`.env.example` 只含变量名与占位符。

### 3.3 启动（lite 档）

```bash
docker compose up -d          # Git Bash（Windows）与 Linux 相同
docker compose ps             # 确认全部 Up
docker compose logs -f gateway   # 观察启动日志，缺关键配置会 fail-fast
```

### 3.4 初始化

| 步骤 | 执行方式 | 内容 |
| ---- | ---- | ---- |
| init-pg | 首次启动自动（挂载 `/docker-entrypoint-initdb.d`，幂等） | 只建库、建扩展（pgcrypto）与权限；**角色/管理员种子唯一走 Alembic 数据迁移 `m1_seed_roles_and_admin`**（随下方 `alembic upgrade head` 执行；[database/01 §8](../database/01-数据库详细设计.md)，角色矩阵见 [08 篇 §2.2](../architecture/08-横切关注点与工程规范.md)——2026-09-26 评审修复G：统一种子时序，init-pg 不再承担种子） |
| init-minio | 首次启动自动（幂等） | 四个 bucket：`raw-docs` / `extracts` / `ontology-artifacts` / `plugin-packages` |
| 数据库结构 | 手工执行 Alembic | 业务表迁移（首批表见锚点 §7 M1） |

```bash
# 业务表迁移（Alembic）
docker compose exec gateway alembic upgrade head

# 手工补建 MinIO bucket（仅 init-minio 未生效时；目标态示例）
docker compose exec minio sh -c \
  "mc alias set local http://localhost:9000 \$MINIO_ROOT_USER \$MINIO_ROOT_PASSWORD && \
   mc mb --ignore-existing local/raw-docs local/extracts local/ontology-artifacts local/plugin-packages"
```

### 3.5 健康检查

```bash
# 网关（Git Bash 与 Linux 相同）
curl -fsS http://localhost:8000/healthz     # 存活探针
curl -fsS http://localhost:8000/docs        # OpenAPI 文档可达

# 存储探活
docker compose exec postgres pg_isready -U ontology
docker compose exec redis redis-cli ping    # 期望 PONG
curl -fsS http://localhost:9000/minio/health/live

# 前端可达（dev 端口；生产走 Nginx 入口）
curl -fsS -o /dev/null -w "%{http_code}\n" http://localhost:5173/
```

全部通过后，用 §3.6 创建的管理员账号登录前端走通一次对话，即完成部署验收（对照锚点 §7 M0 出口条件：compose up 全绿）。

### 3.6 创建首个租户管理员

平台 CLI 为 `onto`（Typer + Rich，只调网关 REST API，见 [docs/cli](../cli/README.md)），可装在任意能访问网关 8000 端口的机器：

```bash
# Git Bash（Windows）与 Linux 相同（参数形态为目标态，以 onto auth bootstrap --help 为准）
pip install -e cli/
export OA_BASE_URL=http://localhost:8000
onto auth bootstrap --email admin@example.com --role admin    # 创建默认租户与首个 admin
```

创建后用该账号登录前端（dev 端口 5173），在 `/system/users` 邀请其余成员并分配角色（users 管理端点待 [docs/api/01](../api/01-REST-API契约.md) 端点登记册登记——登记待办见 §8；2026-09-26 评审修复G：注明依赖）。

### 3.7 各层超时对齐表（2026-09-26 痛点优化，P1）

经典事故：Gunicorn 默认 30s worker 超时杀流式请求；LB 空闲超时低于 SSE 心跳。对齐矩阵（自内向外必须递增）：

| 层 | 参数 | 建议值 | 约束 |
| ---- | ---- | ---- | ---- |
| 任务上限 | ChatPolicy 总预算 | 60s（策略可配） | 基准 |
| Uvicorn worker | timeout-keep-alive | 75s | >任务上限 |
| 反代（Nginx） | proxy_read_timeout | 90s | >worker；`proxy_buffering off` |
| LB/云网关 | 空闲超时 | 120s | >Nginx；>SSE 心跳 15s×多轮 |
| 前端 fetch | AbortController | 120s | 对齐 LB |

部署检查清单加一行：改动任一层超时必须同步本表并跑 TC-SSE 长流用例。

## 4. full 档增量部署

```bash
docker compose -f docker-compose.yml -f docker-compose.full.yml up -d
```

### 4.1 Neo4j（init-neo4j）

- **n10s 插件装法**：`deploy/init-neo4j/` 将 n10s jar 挂载到容器 `plugins/`，并在 `neo4j.conf` 写入：

```text
dbms.unmanaged_extension_classes=n10s.validation.server=/n10s/validation;n10s.rdf.importer=/n10s
```

- **约束与索引**（幂等执行）：

```cypher
CREATE CONSTRAINT n10s_unique_handle IF NOT EXISTS
FOR (r:Resource) REQUIRE r.uri IS UNIQUE;
```

- 注意：多租户隔离走 `tenant_id` 属性 + 复合索引（社区版无多 database/RBAC，§1.2）。

### 4.2 Milvus（init-milvus）

三个 collection（deploy/README）：

| collection | 用途 | 关键契约 |
| ---- | ---- | ---- |
| `kb_chunks` | 文档切片向量 | 维度 = `embedding.dim`；租户隔离 partition key |
| `graph_communities` | GraphRAG 社区摘要向量 | 同上 |
| `memory_embeddings` | 记忆嵌入 | 同上 |

租户隔离 = partition key `tenant_id` + 标量过滤双保险（08 篇 §1）。向量维度必须与 `deploy/config/llm.yaml` 的 `embedding.dim`（bge-m3 = 1024）一致——**改维度必须同步重建 collection**（[07 篇 §2.4](../architecture/07-基础层设计.md)）。健康与指标端口：19530（gRPC）/ 9091（metrics）。

### 4.3 full 档健康检查

```bash
# Git Bash（Windows）与 Linux 相同
curl -fsS http://localhost:7474                      # Neo4j HTTP 可达
docker compose exec neo4j cypher-shell -u neo4j -p "$OA_NEO4J_PASSWORD" "RETURN 1;"
curl -fsS http://localhost:9091/healthz              # Milvus 健康
```

## 5. 升级部署与回滚

### 5.1 升级步骤

```bash
# Git Bash（Windows）与 Linux 相同
git fetch --tags && git checkout <目标版本 tag>
docker compose pull                    # 拉取镜像
docker compose exec gateway alembic upgrade head   # 迁移（先备份，见运维手册 §5）
```

滚动重启顺序：**先存储健康检查（§3.5 探活命令）→ 网关 → 前端**：

```bash
docker compose restart gateway
docker compose up -d --no-deps frontend   # 生产 Nginx：reload 静态资源
```

升级后验证清单：

- [ ] §3.5 健康检查全绿（full 档含 §4.3）；
- [ ] 发起一次对话走通（SSE 流式 + 证据卡片正常）；
- [ ] `docker compose exec gateway alembic current` 与目标版本一致；
- [ ] 若升级触及模型/本体/检索参数/提示词：确认评估回归已跑且未超退化阈值（[08 篇 §7.2](../architecture/08-横切关注点与工程规范.md)）。

### 5.2 回滚步骤

```bash
git checkout <上一版本 tag>
docker compose up -d
```

- 若新版本已执行**不兼容迁移**：停服 → 恢复数据库备份（[运维手册 §5](./02-运维手册.md)）→ 再回退代码；
- 仅当迁移脚本提供 downgrade 时才允许 `alembic downgrade -1`，默认不依赖它回滚。

## 6. 云部署要点

deploy/README 纪律：云/本地双形态（本地 compose vs 云托管 PG/Milvus）**作为配置差异支持，不另建设计**。

| 场景 | 本地 compose | 云托管替换 | 连接配置差异 |
| ---- | ---- | ---- | ---- |
| PostgreSQL | postgres 容器 | RDS / 自建云 PG | `OA_DATABASE_URL` 指向托管端点；开启 SSL；使用托管连接池；**确认 pgvector 扩展可用**（lite 档语义层必需） |
| Milvus | milvus 及其依赖组件 | Zilliz Cloud 等托管向量库 | `OA_MILVUS_URI` 指托管 endpoint；补 TLS/鉴权参数；collection 命名与维度契约不变 |
| 对象存储 | minio 容器 | 云 S3 兼容存储 | `OA_MINIO_ENDPOINT` 换云 endpoint + region；四个 bucket 清单不变（deploy/README）；版本化策略见运维手册 §5 |
| 模型 API | — | 不变 | 渠道 key 经 secret 管理注入（07 篇 §7），不进 `.env` 提交 |

## 7. 常见部署问题 FAQ

| 症状 | 可能原因 | 处置 |
| ---- | ---- | ---- |
| 端口被占用，容器起不来 | 5432/6379/8000 等被宿主进程占用 | `netstat -ano | findstr :8000`（Git Bash）/ `ss -lntp | grep 8000`（Linux）定位后停占进程，或改 compose 端口映射 |
| 网关启动即退出，日志报缺配置 | `.env` 未加载或缺关键变量（fail-fast，07 篇 §7） | 核对 §3.2 变量表；确认 `.env` 与 compose 同目录；`docker compose config` 检查注入 |
| `alembic upgrade head` 失败 | 旧库残留半迁移 / 连接串错误 / 权限不足 | 看报错第一行；确认 `OA_DATABASE_URL`；半迁移状态按 Alembic 版本表修复，必要时从备份恢复（运维手册 §5） |
| MinIO 报权限拒绝 / bucket 不可写 | access key 不匹配 / bucket 未建 / 时钟漂移 | 核对 `OA_MINIO_*`；§3.4 手工补建 bucket；容器与宿主时间同步 |
| Neo4j 容器反复重启或 OOM（full） | 堆内存超宿主可用 | 调 `NEO4J_server_memory_heap_max__size`，预留页缓存；对照 §2.1 硬件建议扩内存 |
| lite 档向量检索报错 | PG 实例缺 pgvector 扩展 | 确认镜像内置 pgvector；在目标库 `CREATE EXTENSION IF NOT EXISTS vector;` 后重试迁移 |
| 前端 5173 打不开 / 接口 404 | dev server 未起；生产环境 Nginx 未反代网关 | dev：`docker compose logs frontend`；生产：检查 Nginx 反代指向 8000（deploy/README：生产由 Nginx 托管静态资源并反代网关） |
| full 档切换后图谱/检索仍走 lite 实现 | 档位开关未生效 / full 服务未起 | 核对 `OA_DEPLOY_TIER=full`；`docker compose -f docker-compose.yml -f docker-compose.full.yml ps` 确认 Neo4j/Milvus 在列；重启网关 |
| 镜像拉取慢/失败 | 网络到镜像源不畅 | 配置镜像加速；大文件拆分提交的推送限制见根 README 注意事项 |
