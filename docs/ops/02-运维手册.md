## 2. 监控体系

### 2.1 OTel 三件套拓扑

统一接 OpenTelemetry SDK，OTLP 导出（[07 篇 §6](../architecture/07-基础层设计.md)）：本地起步导出到文件/Jaeger；生产接现成 APM。trace_id 由 L1 生成 W3C `traceparent` 贯穿 L1→L7（出站模型/MCP 调用、插件信封、异步任务 payload 均携带）；日志统一带 `trace_id` / `tenant_id` 字段。

```text
[L1 前端 traceparent] → [L2 网关中间件解析] → ContextVar 透传
   → L7 出站头（LLM/MCP）→ 插件 daemon 信封 → 任务 payload（worker 恢复父 span）
   → OTLP → Jaeger/APM（一条请求全链检索）
```

导出端配置（目标态示例，变量随 `.env.example` 定稿）：

```bash
# Git Bash（Windows）与 Linux 相同
export OTEL_EXPORTER_OTLP_ENDPOINT=http://jaeger:4317   # 本地 Jaeger；生产替换为 APM endpoint
export OTEL_SERVICE_NAME=oa-gateway
```

### 2.2 指标清单与告警阈值建议

权威清单见 [07 篇 §6](../architecture/07-基础层设计.md)；阈值为运维建议值（待实测冻结）：

| 指标 | 含义 | 建议告警阈值 / 规则 |
| ---- | ---- | ---- |
| `llm_calls_total` | LLM 调用次数（按 tenant/model/profile/status） | 单租户 token 环比 >3x → 人工核查（08 篇 §6 异常检测） |
| `llm_tokens_total` / `llm_cost_usd_total` | token 与成本累计 | 日预算 80% 预警（P2）、100% 触顶（P1）；数据源 `llm_calls` 表 |
| `llm_latency_seconds`（histogram） | LLM 调用延迟 | P95 连续 15min 超基线 +50% → 观察（P2） |
| `llm_cache_hit_ratio` | prompt caching 命中率 | 低于租户基线关注（成本异常信号） |
| `mcp_tool_calls_total` | MCP 工具调用（按 direction/status） | 错误率 >50% → 熔断自动开路（07 篇 §3） |
| `mcp_tool_latency_seconds` | 工具调用延迟 | P95 超阈值 → P2 |
| `mcp_circuit_state` | 熔断状态（0=closed/1=open/2=half-open） | =1 (open) 持续 >5min → P1 |
| `kb_retrieval_latency_seconds` | 检索延迟（按 mode） | P95 超基线 → P2 |
| `degraded_retrievals_total` | 降级检索计数 | 速率突增 → P1（08 篇 §6） |
| `task_duration_seconds` | 异步任务耗时（按 task_type） | 超流水线超时预算（03 篇 §4）即失败处理并告警 |
| `task_retry_total` | 任务重试计数 | 单租户重试率突增 → P2 |
| `outbox_dead_total` | outbox 死信（M4 起，03 篇 §6.2） | 积压 >100 → **P0**（08 篇 §6） |
| `plugin_invoke_total` / `plugin_quota_exceeded_total` | 插件调用 / 配额超限 | 配额接近 → P2；超限事件留 `tool_invocations` 痕迹 |

### 2.3 大盘设计（五块）

| 大盘 | 核心内容 | 数据源 |
| ---- | ---- | ---- |
| 服务健康 | 网关 QPS / 5xx 率 / 延迟、SSE 连接数、五存储探活、熔断状态 | OTel + 探针 |
| LLM 成本 | token / 费用趋势、按模型与租户占比、缓存命中率、fallback 切换次数 | `llm_calls`（07 篇 §2.3） |
| MCP 调用 | 工具维度调用量 / 延迟 / 错误率、熔断开路清单 | `tool_invocations` + `mcp_*` 指标 |
| 流水线积压 | `kb:queue:{tenant_id}` 队列长度、七步状态分布、失败/重试任务 | Redis + `kb_pipeline_step`（03 篇 §4） |
| 回写台账状态（M4 起） | `writeback_ledger` 各 status 行数、unknown 存留时长、`needs_human` 队列深度 | `writeback_ledger`（回写设计 §8） |

## 3. 告警分级

定义权威在 [08 篇 §6](../architecture/08-横切关注点与工程规范.md)（触发行为对齐 §5 降级矩阵）：

| 级别 | 触发示例（权威清单） | 通知方式 | 响应 SLA |
| ---- | ---- | ---- | ---- |
| **P0** | 五存储任一不可用、outbox dead 积压 >100 | 值班电话 / 短信 | 15 min 响应，持续处置 |
| **P1** | 租户预算触顶、MCP 熔断 open、降级事件率突增 | IM 群机器人 | 1 h 内响应 |
| **P2** | 降级事件汇总、慢查询、配额接近 | 日报邮件 | 当日处理 |

每级示例告警与第一响应动作：

| 级别 | 示例告警 | 第一响应动作 |
| ---- | ---- | ---- |
| P0 | `postgres` 探活连续失败 / `outbox_dead_total` 超 100 | 确认影响面（哪个租户/哪条链路）→ 对应 §6 Runbook 条目 → 每 30 min 在事故群同步 |
| P1 | 某 MCP server 熔断 open 超 5min / 某租户预算触顶 / `degraded_retrievals_total` 速率突增 | 定位租户/依赖组件 → 按 §6⑦（预算）或 §6⑥（依赖不可用）处置 → 记录进当值日志 |
| P2 | 降级事件日报汇总 / PG 慢查询 top10 / 插件配额接近 | 登记工单，纳入周检复盘（§4.2） |

## 4. 日常巡检

### 4.1 日检

| 项目 | 检查方式（目标态示例） | 关注点 |
| ---- | ---- | ---- |
| 存储水位 | `df -h`（Linux）/ 磁盘属性（Windows）；`docker compose ps` | 磁盘使用 >80% 预警、容器重启计数 |
| 队列积压 | Redis `LLEN kb:queue:{tenant_id}`（03 篇 §4） | 长度持续增长 = 消费停滞 |
| 死信 | `outbox_dead_total` 告警 / `tasks` 表 failed 计数 | >0 即查 §6④ |
| 对账差异（M4 起） | 回写日对账报告（回写设计 §4） | 未闭环差异数 |
| 巡检任务结果 | 本体一致性 / SHACL 定期巡检任务 | 新增违例数（终态归 pending_review 由人工裁决，03 篇 §4） |
| 备份完成 | 备份任务日志 / 对象存储清单 | 当日备份成功（§5） |

日检常用命令（目标态示例，Git Bash 与 Linux 相同）：

```bash

docker compose ps --format "table {{.Name}}\t{{.Status}}"   # 重启计数
docker compose exec redis redis-cli --scan --pattern "kb:queue:*"   # 抽取队列 key
docker compose logs --since 24h gateway 2>&1 | grep -ci error      # 错误日志量级
```

## 5. 备份与恢复

### 5.1 备份对象与策略

| 对象 | 方式 | 频率 | 保留 | RPO / RTO 目标 |
| ---- | ---- | ---- | ---- | ---- |
| PostgreSQL（权威库） | `pg_dump` 全量 + WAL 归档 | 全量每日 1 次；WAL 连续归档 | 全量 14 份，归档 ≥30 天 | RPO ≤ 5 min / RTO ≤ 1 h |
| MinIO 制品 | 版本化 + 跨盘（或跨站）复制 | 实时 | 按版本策略 | RPO ≈ 0 / RTO ≤ 2 h |
| Neo4j（full 档） | `neo4j-admin database dump` | 每日 | 14 份 | RPO ≤ 24h / RTO ≤ 2 h（可由 TBox 制品 + outbox 重放物化，锚点 §3.2：Neo4j 是物化视图） |
| Redis | RDB 快照（可选） | 每小时 | 2 份 | 非权威数据：L1 可由 PG messages 重建（08 篇 §5 降级路径） |

备份执行命令（目标态示例，Git Bash 与 Linux 相同；生产应固化为定时任务）：

```bash
# PG 全量
docker compose exec -T postgres pg_dump -U ontology -Fc ontology > backup/ontology_$(date +%Y%m%d).dump
# Neo4j（full 档）
docker compose exec neo4j neo4j-admin database dump neo4j --to-path=/data/backups
# MinIO 版本化与跨盘复制在存储侧配置（桶策略），不依赖定时任务
```

### 5.2 PG 点位恢复演练（每季度）

```bash
# 0) 停写入（Git Bash 与 Linux 相同）
docker compose stop gateway
# 1) 恢复最近一次全量备份
docker compose exec -T postgres pg_restore -U ontology -d ontology < backup/ontology_20260925.dump
# 2) 配置 WAL 回放至目标时间点（recovery_target_time = 事故前一刻），重启 PG 完成回放
# 3) 验证：关键表行数 / 最新 changeset 状态 / audit_logs 连续性
docker compose exec postgres psql -U ontology -d ontology -c "SELECT count(*) FROM audit_logs;"
# 4) 恢复服务并核对 SSE / 检索链路
docker compose start gateway
```

演练结论（实际 RTO、数据损失窗口）登记进审计与本文待办。

## 6. 故障处理 Runbook

每例按「症状 → 诊断 → 处置 → 预防」；通用纪律：**主对话链路永不因辅助依赖失败而中断，一切降级必须显式标注，禁止静默降级**（08 篇 §5）。

### ① 网关 5xx 激增

- 症状：5xx 比例突增（服务健康大盘），用户侧请求失败。
- 诊断：`docker compose logs --since 30m gateway | tail -100`；按 trace_id 取最慢链路；区分「依赖故障传导」与「自身缺陷」（最近是否有变更，§9）。
- 处置：依赖故障走对应条目（⑥/⑦）；自身缺陷 → 回滚最近版本（部署手册 §5.2）；单实例过载 → 扩网关副本（SSE 多副本 M3 已验证）。
- 预防：变更灰度 + 评估回归门禁（08 篇 §7.2）。

### ② SSE 全断

- 症状：全部会话流式输出中断，前端反复重连。
- 诊断：`docker compose ps gateway`（是否重启循环）；服务健康大盘 SSE 连接数跌零；`curl -fsS http://localhost:8000/healthz` 排除进程级故障。
- 处置：重启网关（SSE 长流程全程不持事务，重启安全，03 篇 §6.1）；前端自动重连（目标 <5s，§1.1）；重连期间消息以会话消息接口拉齐（补偿策略见 frontend/02 待办）。
- 预防：网关内存/连接数水位告警；多副本分散连接。

### ③ 流水线 stuck

- 症状：文档长时间停在某状态不推进（P3/P2 页面可见）。
- 诊断：

```sql
-- kb_pipeline_step（03 篇 §4）
SELECT document_id, step, status, error, updated_at
FROM kb_pipeline_step
WHERE status = 'running' AND updated_at < now() - interval '1 hour';
```

对照超时预算（预处理 10min / 抽取 60min / 对齐 20min / 校验 10min）；检查 worker 存活与 LLM 渠道可用性。

- 处置：步内重试耗尽已自动置 `failed` 并告警 → 人工修复后经 `pipeline/retry` **从断点步骤继续**（checkpoint 在 PG，中间产物在 MinIO，重跑自动跳过已完成步骤）；worker 死亡则重启消费进程。
- 预防：超时预算自动置失败 + 告警（03 篇 §4）；队列积压纳入日检。

### ④' 对账任务自检（2026-09-26 模块审计补）
症状：`writeback_recon_diff_total` 连续 2 天无新值 = 日对账未跑。处置：查 ARQ/队列 worker 存活与 lease；对账跳过超过 48h 升 P1 手工补跑（业务回写设计 §4 脚本）。预防：`recon_last_success_age` gauge 告警 >36h。

### ④ outbox 积压（M4 后）

- 症状：`outbox_dead_total` 上升或 `published_at IS NULL` 行数持续增长；>100 触发 **P0**。
- 诊断：`SELECT count(*) FROM outbox_events WHERE published_at IS NULL;`（03 篇 §6.2）；检查 relay 后台任务与 Redis 选主锁（多实例时单 worker 选主）。
- 处置：重启 relay 进程；死信按人工补偿重放——消费方按 `event_id` 幂等去重，重放安全；投递语义至少一次 + 同聚合按 id 保序。
- 预防：relay 存活与选主状态纳入服务健康大盘。

### ⑤ 回写 unknown 态堆积 → 对账流程（M4 后）

- 症状：`writeback_ledger` 中 `status=unknown` 行数增长（投递超时/响应丢失）。
- 诊断：

```sql
-- writeback_ledger（回写设计 §8）
SELECT status, count(*) FROM writeback_ledger GROUP BY status;
SELECT idempotency_key, updated_at FROM writeback_ledger
WHERE status = 'unknown' AND updated_at < now() - interval '1 hour';
```

- 处置（**禁止盲目重试**——重复创建工单/订单是回写最典型事故源，回写设计 §2.5）：
  1. 先按幂等键 `query_status` 核实业务侧真实状态（`{tenant_id}:{action_instance_id}`）；
  2. 能判定 → 落终态（succeeded/failed）；不能判定 → 进对账队列；
  3. 对账走[业务回写设计 §4](../MCP/业务回写设计.md) 日对账：台账 vs `query_status` 比对 → 差异分类 → 自动核实（重查 + 时间窗判定）→ 可判定则补记终态或触发补偿（业务冲正），不可判定进人工干预队列；
  4. unknown 超过对账时限（默认 24h）→ `needs_human=true` 人工干预（重发同幂等键 / 标记冲正 / 关闭附理由，全部留审计）。
- 预防：`unknown_recheck_seconds=300` 自动重核（回写设计 §3.1）；unknown 存留时长纳入回写台账大盘。

### ⑥ Milvus / Neo4j（full 档）不可用 → 降级矩阵动作

- 症状：图查询或向量检索失败告警；用户侧回答出现「证据链暂缺」标注。
- 诊断：`curl -fsS http://localhost:9091/healthz`（Milvus）；`curl -fsS http://localhost:7474`（Neo4j）；容器资源（Neo4j OOM 常见，部署手册 §7）。
- 处置：按[08 篇 §5 降级矩阵](../architecture/08-横切关注点与工程规范.md)执行——**Neo4j 不可用**：`knowledge.search` 自动降级纯向量检索，`degraded=True`；**Milvus 不可用**：退化为纯图检索（实体邻域 + 社区摘要）；**全不可用**：跳过上下文并在回答中标注。运维职责是尽快恢复依赖并观察 `degraded_retrievals_total` 回落。
- 预防：full 档存储资源水位监控；降级行为的注入测试纳入 CI 冒烟（08 篇待办）。

### ⑦ LLM 网关超配额 → 预算降级链

- 症状：租户预算触顶（P1 告警）；用户收到超限提示或回答质量下降（被降级 light 模型）。
- 诊断：`llm_cost_usd_total` 按 tenant 聚合（大盘「LLM 成本」）；`llm_calls.status` 与 fallback 切换计数。
- 处置链（07 篇 §2.3）：日预算 **80% 预警**通知租户管理员 → **100% 自动降级 `light` 模型** → 超限拒绝新调用并在响应中提示（可按租户配置放宽）。异常消耗（单租户环比 >3x）按滥用/注入攻击放大核查（08 篇 §6）。
- 预防：预算与限流配置随租户 onboarding 校准；月度成本归因报表（周检）。

### ⑧ 存储磁盘水位

- 症状：磁盘使用率告警（>80% 预警 / >90% 紧急）。
- 诊断：

```bash
# Git Bash（Windows）与 Linux 相同
df -h                          # 整体水位
docker system df               # 镜像/卷/构建缓存占比
docker compose exec postgres psql -U ontology -d ontology -c \
  "SELECT pg_size_pretty(pg_database_size('ontology'));"   # PG 体积
```

进一步定位到具体存储（PG WAL 堆积、MinIO 制品、Neo4j 存储、容器日志）。
- 处置：PG → 归档清理 + `VACUUM`；MinIO → 生命周期策略清理过期制品；日志 → 轮转上限；仍不足 → 扩容（§8 触发表）；>90% 时优先保 PG（权威库），可暂停抽取流水线入队降低写入。
- 预防：日检水位 + §8 容量规划提前触发扩容。

## 7. 安全运维

### 7.1 密钥轮换流程

1. 新密钥在 secret 管理（Vault/云 KMS）生成（07 篇 §7）；
2. 注入新值并滚动重启网关（模型渠道 key 可新旧并行观察一个窗口）；
3. 验证旧 key 已失效（模型渠道侧吊销；外部 MCP server 凭据在 `infra/security` 加密存储更新）；
4. 轮换事件落审计（08 篇 §3 认证类）。

### 7.2 JWT 密钥轮换与会话影响

- 令牌参数：access 2h / refresh 14d（08 篇 §2.1）；
- 轮换后**旧 access 在其自然过期前仍有效**——需要立即失效时配合 `jti` 吊销黑名单（Redis，TTL = 剩余有效期）批量拉黑；
- refresh 令牌随轮换失效，用户需重新登录；选择低峰窗口执行并提前通知租户管理员。

### 7.3 审计导出与漏洞响应

- 审计导出：前端 `/system/audit` 只读，导出走任务中心（frontend/02 P12）；在线热数据 90 天后转冷归档（对象存储）保存 ≥3 年，**不允许调低**（08 篇 §3）。
- 漏洞响应：隔离（插件沙箱出网白名单/停用可疑插件）→ 影响评估（按 trace_id 溯源 `tool_invocations` 与 `audit_logs`）→ 修补发布（§9 紧急通道）→ 复盘留审计。
