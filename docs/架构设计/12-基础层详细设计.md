# 12 - 基础层详细设计（模型网关 / 事件 / 队列 / 可观测 / 配置）

> 状态：v1.0 待评审 | 日期：2026-09-26 | 上游依据：01 篇 §1 foundation 目录、00 篇 §3 选型
>
> 本文定稿基础层六件套的接口与实现策略。原则：基础层是**无业务语义的横切原语**，只被上层依赖、绝不反向依赖（01 篇 §1.1 禁令：foundation 禁止依赖以上任何业务层）。

---

## 1. 模块定位与边界

落位 `backend/app/foundation/`（01 篇 §1），六件套清单：

| # | 子模块 | 职责 | 对上层暴露 | 禁止 |
| ---- | ---- | ---- | ---- | ---- |
| 1 | `config` | pydantic-settings 分层配置、密钥文件读取（§6） | 类型化 `Settings` 单例 | 运行时写配置、静默吞校验错误 |
| 2 | `logging` / `telemetry` | 结构化日志、OpenTelemetry 采集、trace_id 工具（§5） | `get_logger()` / tracer / 指标注册 | 落敏感明文（§5.4 脱敏清单） |
| 3 | `llm` | 模型网关：统一接口、渠道与凭据、预算/限流/降级、成本记账、Claude 直连开关（§2） | `ModelGateway` Protocol | 感知业务语义（用途仅作记账标签） |
| 4 | `events` | Redis Streams 发布/消费框架、Outbox 中继（§3） | `publish()` / 消费者基类 / 事件信封 | 定义事件语义（事件类型由业务层定义） |
| 5 | `queue` | ARQ 任务注册、cron 装配、双队列装配（§4） | 任务注册装饰器、worker 工厂 | 实现任务体（任务体在 application 层） |
| 6 | `security` | JWT 签发校验、密码哈希、API Key 生成校验 | 无状态工具函数 | 用户/角色等业务模型（归 domain/iam） |

依赖铁律：六件套内部只允许 `config` / `logging` 被其余五件依赖，`llm` / `events` / `queue` / `security` 互不 import；全层不得 import `gateway / application / domain / semantic / data`（00 篇 §2 分层依赖方向：只有上层依赖下层）。

## 2. 模型网关（LiteLLM SDK 内嵌）

选型定稿（00 篇 §3）：v1 LiteLLM **SDK 内嵌**减少部署组件，接口按 Proxy 形态设计以便平滑切换（§2.6）。

### 2.1 统一接口 Protocol（上层只认这四个方法）

```python
class ModelGateway(Protocol):
    async def complete(self, req: LlmRequest) -> LlmResponse: ...
    async def stream(self, req: LlmRequest) -> AsyncIterator[LlmChunk]: ...
    async def embed(self, req: EmbedRequest) -> EmbedResponse: ...   # 统一 bge-m3 类模型（02 篇 §4）
    def route(self, ctx: RouteContext) -> Channel: ...               # 按用途/租户/预算选渠道，不发起调用
```

`LlmRequest` 必带：`tenant_id / user_id / session_id / purpose(online|background) / trace_id / model_hint / max_tokens`——预算与记账的全部键都在请求里，调用方不接触渠道与凭据。`purpose=background` 的调用走独立预算（06 篇 §5.5.3）。

### 2.2 渠道与凭据管理

表沿用 02 篇 `model_providers / model_channels`（provider, base_url, credential_ref, budget, priority, enabled），语义定稿：

- `priority`：fallback 顺序（小者优先，§2.3 链式降级依据）；
- `credential_ref`：只存密钥引用，实际密钥经环境/secrets 注入（14 篇 §3），**库内零明文**；
- `enabled`：渠道总闸（Claude 通道为双闸之一，§2.4）；
- 价目（输入/输出单价）随渠道配置版本化，供 `llm_calls.cost` 折算。

### 2.3 预算 / 限流 / 降级

- **预算**：租户级月预算（`tenants.plan` + 渠道 budget），`online` 与 `background` 分账记账（06 篇 §5.5.3：后台配额独立、可单独熔断，记忆任务挤不掉在线对话配额）。用量 = Redis 实时计数 + `llm_calls` 汇总对账；
- **限流**：租户 × 渠道的 RPM / 并发上限，Redis 滑动窗口（复用 02 篇 `rl:` 键空间）；
- **降级**（fallback 链示例）：

```
主渠道（priority=1）
  → 超时 / 429 / 5xx → 备用渠道（priority=2）
  → 仍失败 → 规则降级：返回固定模板 + "模型暂不可用"提示；
              复杂语义判断类请求转待办——候选非成品不降质，只延迟（设计宪法第 3 条）
```

- **熔断**：单渠道连续失败 ≥5 次冷却 60s（初值），期间 `route()` 直接跳过该渠道。

### 2.4 Claude 直连通道

`model_channels` 预留 Anthropic 直连渠道，**默认 `enabled=false`**；开启需双闸：渠道行 `enabled` + 环境变量 `ONTO_AGENT_LLM_CLAUDE_ENABLED`（§6.3）。00 篇风险登记：Claude Agent SDK 专有条款与计费变动，**法务确认前不得开启**；pi/nanobot 作 MIT 备选运行时，不依赖此通道。

### 2.5 成本记账（llm_calls 表，PG 新增）

| 列 | 说明 |
| ---- | ---- |
| `id / tenant_id / user_id / session_id` | 归因键（租户/用户/会话三级成本归因，00 篇 补2） |
| `model / channel_id` | 请求模型与**实际命中渠道**（fallback 后的真实渠道） |
| `input_tokens / output_tokens` | 计费两口径 |
| `cost` | 按渠道版本化价目折算 |
| `latency_ms / trace_id` | 性能与全链路关联（§5.2） |
| `purpose` | `online / background`（06 篇分账） |
| `created_at` | —— |

写入口径：网关唯一出口统一埋点；记账失败不阻塞调用返回（异步补记，失败入死信），预算实时检查以 Redis 计数兜底。

### 2.6 LiteLLM Proxy 切换触发条件（建议值，待评审）

满足任一即评估切换：渠道数 > 5 且多租户价目管理成本显著；backend 多实例部署需要集中凭据与配额；需要独立控制面（预算面板、渠道级日志）；LiteLLM SDK 升级频繁冲击主服务发版节奏。切换只改 `foundation/llm` 适配层（接口已按 Proxy 形态设计，00 篇 §3），上层零改动。

## 3. 事件总线（Redis Streams + Outbox，ADR-7）

### 3.1 stream 命名约定

`oa:events:{domain}`，domain ∈ `kb / memory / approval / plugin / action / platform`；消费组按模块划分（02 篇 §6）。02 篇 §6 键空间已同步本分域命名（原单流键 `stream:events` 废弃）。

### 3.2 事件信封 schema（JSON 示例）

```json
{
  "event_id": "0197c7a2-8f3e-7d10-9a2b-3c5d6e7f8091",
  "tenant_id": "0197b100-4a55-7c21-8d90-1e2f3a4b5c6d",
  "type": "kb.community.dirty",
  "occurred_at": "2026-09-26T08:30:00Z",
  "payload": { "kb_id": "kb-001", "community_ids": ["c-12", "c-13"] },
  "trace_id": "7bf3a1e0c2d94e5f8a6b7c8d9e0f1a2b"
}
```

`event_id` 全局唯一（UUIDv7，时间有序），是消费端幂等去重与 Outbox 投影去重的唯一依据（02 篇 §7：按 event_id 去重）。

### 3.3 Outbox 实现（可靠出站）

```
业务事务：写业务表 + outbox_events（同事务提交，01 篇 data/uow.py、02 篇 outbox_events(state=pending/sent)）
  → relay 进程轮询 outbox_events(state=pending)（索引 outbox_events(state)，02 篇 §2）
  → 按 domain XADD 到 oa:events:{domain}
  → 标记 sent
```

投递失败重试 5 次（指数退避）→ 死信流 + 通知；**绝不因投递失败回滚主事实**（02 篇 §7 铁律）。relay 单实例运行（Redis 锁防重）。

### 3.4 消费端框架

- **消费者组**：每模块一个 group（`kb-projection / memory-pipeline / approval-watcher / notify`），`XREADGROUP + XACK`；
- **幂等键**：`event_id`（去重表 / Redis `SETNX`，TTL 7d）+ 业务键（如 `document_id + stage`）双保险（对齐 06 篇 §5.5.3）；
- **重试退避**：处理异常不 ACK，pending 列表按 1s/4s/16s/…上限 5min 重投，5 次后入死信；
- **死信**：`oa:events:dlq` 留原始信封 + 错误摘要，管理端人工重放。

### 3.5 初版事件清单

| type | 生产方 | 主要消费方 | 用途 |
| ---- | ---- | ---- | ---- |
| `action.result.returned` | application/action_service | 语义层投影 / 记忆 | 行动回流：本体实例 + 记忆 + 审计落账（01 篇 2.5） |
| `session.ended` | Agent 服务 | memory_pipeline | 记忆沉淀触发：L1→L2 三步（06 篇 §5.1） |
| `approval.state.changed` | approval_service | 通知 / 各业务模块 | 审批状态变更（四/五类审批对象统一，01 篇 2.7、04 篇 §9） |
| `plugin.state.changed` | 插件服务 | 工具注册中心 / 通知 | 上下架 / 停用 / 失败熔断（05 篇 §3.2） |

## 4. 任务队列（ARQ）

选型定稿（00 篇 §3）：ARQ（async 原生；Celery 同步模型与 FastAPI 混用别扭不选）。队列拓扑沿用 06 篇 §5.5.2 **双队列**：`arq:queue:online` / `arq:queue:idle`（空闲闸门四信号 + 低峰直通 + deadline 兜底），v1 同镜像起两个 worker 进程（编排见 14 篇 §1）。任务体一律在 application 层实现，`foundation/queue` 只负责注册与装配。

### 4.1 任务注册表与超时/重试/幂等策略

| 任务 | 队列 | 触发 | 超时 | 重试 | 幂等键 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| `kb.step.preprocess`（同源检测+格式转换/OCR） | online | 文档上传 | 30min | 2 次（stage 级，04 篇 §3） | document_id + content_hash |
| `kb.step.extract`（批量抽取） | online | 上一步完成 | 60min | 3 次 | job_id + batch 序号；排队走 online，LLM 记账记 background（18 篇 §9），不占对话预算 |
| `kb.step.align_terms`（术语对齐） | online | 上一步完成 | 30min | 3 次 | job_id + step |
| `kb.step.checks`（一致性+约束校验） | online | 上一步完成 | 30min | 2 次 | job_id + step |
| `kb.step.archive`（终审归档执行） | online | 终审通过 | 10min | 3 次 | job_id |
| `memory.extract_candidates / align_and_resolve / write_l2`（沉淀三步） | idle | session.ended | 30min/步 | 3 次 | session_id + task_type + batch_id（06 篇 §5.5.3） |
| `memory.decay_scan`（衰减调度器） | idle | cron 每小时 | 10min | 单实例锁 | 扫描窗口起止 |
| `rules.materialize`（SPARQL CONSTRUCT 物化） | idle | 规则/本体版本发布事件 | 60min | 2 次 | ontology_version + rule_id |
| `kb_nightly_maintenance`（nightly 维护例程：增量重编译 + lint + 冲突补扫，04 篇 §5.2） | idle | cron 每夜（租户级可配频率） | 4h | 1 次 + deadline 升级在线 | tenant_id + 运行日 |

通用规则：重试耗尽 → 失败事件 + 通知；所有后台任务带 deadline，到期仍未执行自动升入在线队列（06 篇 §5.5.2——空闲是优化项，不是无限期推迟）。

## 5. 可观测

### 5.1 OpenTelemetry 采集点清单

| 采集点 | 形态 | 关键属性 |
| ---- | ---- | ---- |
| FastAPI 中间件（网关层） | server span | route、tenant_id、status_code |
| httpx 出站 | client span | 目标类型（LLM / 业务 API / 插件内部 API） |
| 语义层关键函数 | 函数 span | SHACL 校验 / 规则物化 / DL 推理 / GraphRAG 检索各自独立 span（推理分级可观测化） |
| LLM 调用（foundation/llm） | 独立 span | model、channel、tokens、cost、purpose |
| ARQ 任务 | job span | 任务名、队列、重试次数 |
| 事件消费 | consumer span | stream、group、event_id |

### 5.2 trace_id 贯穿规则

HTTP 入口（W3C `traceparent` / `X-Request-Id`，缺失则生成）→ 网关中间件绑定请求上下文 → 出站调用与 LLM 调用透传 → **事件信封 trace_id 字段**（§3.2）→ 消费端续链 → 落 `audit_logs.trace_id` 与日志字段（01 篇 §4；05 篇 §3.1 MCP 审计留痕）。跨进程（ARQ 任务、relay）经任务参数/事件信封传递，**不允许出现无 trace 的后台写入**（06 篇 §5.5.4：后台操作审计带 `trigger=idle_worker` 标记）。

### 5.3 指标清单

- **RED 三项**：每路由请求数 / 5xx 错误数 / 时延分位（P50/P95/P99）；
- **业务指标**：抽取吞吐（jobs/h + 各 stage 耗时）、审批积压（pending 工单数按类型）、工具成功率（MCP/本地/业务 API 分维度，01 篇 2.6 观测反哺市场排序）、LLM 成本（租户 × online/background）、SSE 在线连接数与断连率、后台四指标（排队时长 / deferred_count / 空闲窗口利用率 / 后台 LLM 成本占比，06 篇 §5.5.4）。

暴露：backend / worker 同镜像暴露 `/metrics`（Prometheus 格式）；抓取与告警基线见 14 篇 §5。

### 5.4 结构化日志规范

- JSON 行：`{ "ts", "level", "logger", "trace_id", "tenant_id", "user_id", "module", "msg", "extra" }`；开发环境可切文本（§6.3 `LOG_FORMAT`）；
- **脱敏字段清单**（logging 过滤器强制）：password、token / api_key、Authorization / Cookie 头、渠道凭据值（`credential_ref` 只记引用不记值）、记忆正文与文档正文（默认只记 record_id / document_id，不落内容）、手机号/身份证号等 PII（掩码：前 3 后 4 之外以 `*` 替换）。

## 6. 配置管理

### 6.1 分层与优先级（pydantic-settings）

四层，从低到高：**代码默认值（defaults）→ .env 文件（本地/Compose 缺省）→ 环境变量（容器注入，覆盖 .env，与 pydantic-settings 默认次序一致）→ 环境专属覆盖文件（`settings.{dev,staging,prod}.toml`，显式声明才生效）**。校验失败启动即报错（fail-fast），禁止运行时静默回落默认值。

### 6.2 前缀约定

服务端配置统一前缀 **`ONTO_AGENT_`**（pydantic-settings `env_prefix`）。`OA_` 前缀保留给 `oa` CLI 客户端的三个环境变量（`OA_ENDPOINT / OA_API_KEY / OA_OUTPUT`，05 篇 §4.2）——CLI 是平台外的独立进程，与同机部署的服务端进程互不污染。
