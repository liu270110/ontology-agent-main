## 1. 设计目标与六条公理

回答五个问题：①知识来源全景是否盘点清楚（§2）；②各类源怎么分场景接入（§4）；③业务系统如何"ontology 方式接入 + 零侵入 + 同步的资源效率统一"（§4.1）；④适配器框架长什么样（§3）；⑤同一句话在不同系统含义不同怎么办（§5）；⑥知识库如何是动态的、能指导和推理下一步（§6）。

| # | 公理 | 说明 |
| ---- | ---- | ---- |
| 1 | **接入 ≠ 入库** | 一切源经连接器 → 统一信封 → Raw 层（不变）→ 既有七步流水线；门禁（候选非成品/SHACL/术语唯一/终审）对全来源一致，不因来源可信而跳过 |
| 2 | **只读不侵入** | 平台对一切源系统**零写权限**；平台对业务系统的唯一写通道 = MCP `action.invoke` + 审批中心（锚点既有），且该通道与连接器**账号、网络、代码三重物理分离** |
| 3 | **适配器可插拔（分级）** | 连接器 = 平台插件：复用插件运行时隔离、凭据自持（07 篇密钥机制）；**涉高敏凭据的连接器（CDC/REPLICATION 类）只允许内置/官方认证渠道，不开放生态市场** |
| 4 | **分级同步** | 不存在"全源实时全量"——按 源变更频率 × 知识价值密度 × 消费时效要求 定 SLA 分级（§4.1 四级），成本护栏硬上限；**SLA 是尽力而为：源侧保护优先于知识新鲜度**（公理 2 的从属条款） |
| 5 | **语义进本体** | 一切"同词异义"在术语语境层统一解决（§5），连接器只忠实携带 `source_system`，不自行翻译语义 |
| 6 | **动态闭环** | 接入 → 知识 → 推理 → 行动 → 回流 → 知识（OB2 逆向闭环）；知识使用数据反哺接入优先级（§6.1 活性环） |

## 2. 知识来源全景（六类源盘点）

### 2.0 接入可行性总红线（先于一切源盘点）

1. **安全分区红线（电力场景第一课）**：调度 SCADA / 配电自动化主站位于**生产控制大区**，受电力二次安防规定约束——**平台不直连、不申请直连、连评估请求都不发起**。生产大区数据一律经**隔离装置单向文件摆渡**（E 语言 / CIM / XML / 报表导出）落地，按 ①类文件源通道进流水线——**文件通道不是低配，是电力场景的正规军**。每源接入前先确认其安全分区归属，分区结论进源准入评审单。
2. **最差可行路径（永远在线的降级档）**：企业现实 = 接口不开放（供应商锁定）、只读账号审批以月计、内网隔离。⓪类人工通道（导出文件/报表/截图/手工上传）是**每个源的兜底路径且永远在线**——连接器是增强不是前提。审批周期 > 2 周（示例值）的源立即切文件导出兜底，不在审批上死等。

### 2.1 六类源盘点

| 类 | 典型系统 | 数据特性 | 变更驱动 | 价值密度 | 默认接入模式（详见 §4） | 最差可行路径 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| ① 文档型 | 文件管理系统/DMS、网盘、Wiki/Confluence、**合同系统** | 非结构化/半结构化，版本化 | 人驱动（低频） | 中高 | 增量扫描/watch → 拉取落 Raw | 人工导出上传 |
| ② 业务事务型 | 业务数据库（ERP/PMS/营销/工单） | 强结构化，schema 权威 | 事务驱动（高频） | 分化大（按表评审） | 快照 diff / 增量轮询 / CDC → 中转区 | 脱敏快照导出文件 |
| ③ 数据中台 | 数仓、指标平台、数据湖 | 结构化 + **指标口径语义** | 批处理（T+1/小时） | 高（口径=规则类） | 批拉取（API/表订阅/物化视图） | 报表导出 |
| ④ 消息型 | 邮件系统、企微/钉钉/飞书 | 非结构化+附件，**权限最敏感** | 事件驱动 | 中 | 显式投递 + 受控订阅 | 转发到平台投递地址 |
| ⑤ 外部型 | 爬虫系统（外部标准库/政策/竞品） | 非结构化，可信度参差 | 调度爬取 | 中 | 准入暂存 → 分级审核 | 手动保存网页上传 |
| ⑥ 机器型 | 日志/监控/告警/**生产事件流** | 半结构化、海量、时效强 | 实时流 | 原始低/**蒸馏后高** | 三档分流（见下） | 值班报表/截图上传 |
| ⓪ 人工 | 平台上传、手动导入 | 任意 | 人驱动 | 高 | 已有能力（MinIO raw-documents + 流水线） | ——（它就是兜底） |
| 补 | 音视频（95598 座席录音）、图纸/GIS/CAD | 多模态 | 低频 | 中 | **v1 不做，v2 评估**（多模态抽取就绪后经①通道） | 关键件人工转写上传 |

**⑥机器型内部三档分流**（防"停运事件"这类 wedge 核心知识被"原始不入库"误伤）：

| 档 | 内容 | 处置 |
| ---- | ---- | ---- |
| 量测流 | 高频数值遥测（电压/电流/负荷曲线） | **不入库**（易变、海量）——只存查询指针，实时取数（主文档 §8.5） |
| **事件流** | 离散状态变更（停运/复电/遥信变位/告警升起） | **可入库**（低频高价值）——经 §4.1 通道成事实，是 §6.2 next_actions 的主要触发源 |
| 蒸馏知识 | 故障模式（症状→根因→处置）、告警规则 | 挖掘/人工沉淀 → 候选审核入库 |

> 盘点纪律：全景允许裁剪（v1 不做即标"v2 评估"），不允许遗漏不表态。

## 3. 连接器框架（适配器契约）

### 3.1 统一接口与统一信封

```python
class SourceConnector:                       # 所有连接器实现同一契约
    def capabilities(self) -> ConnectorCaps  # cdc/webhook/incremental/full 支持矩阵
    def discover(self) -> SourceManifest     # 源清单 + schema_profile + schema_fingerprint
    def fetch(self, cursor) -> list[SourceEvent]   # 增量拉取，幂等
```

统一信封 **SourceEvent**（连接器与流水线的唯一交接面，字段完备性在此一次定稿）：

| 字段 | 说明 |
| ---- | ---- |
| `source_type / source_id / source_system` | 六类源枚举 / 连接器实例 / **语境维度**（§5，取值注册表见 §5.1） |
| `stream_id` | 源内流标识（表名/清单项/文件夹）——**幂等去重三元组锚 = (source_id, stream_id, external_id)**（一个业务库多表各有主键，单 external_id 不完整） |
| `external_id` | 源系统业务主键（与 stream_id 合用；删除传播锚点） |
| `source_sequence` | 源端单调序号（LSN / binlog offset / 水位值）——**乱序防护**：晚到的旧事件不得复活已 tombstone 记录 |
| `event_type` | `added / modified / deleted / schema_changed`（删除=tombstone 永不物理删，走主文档 §8.2 失效语义；schema 演进见 §4.1） |
| `payload_ref / payload_hash` | 落地区指针 + 内容哈希（追溯锚：landing 90 天滚动后，`kb_connector_events` 登记行 + 哈希是唯一追溯凭据） |
| `schema_fingerprint / connector_version` | 列名/类型哈希 + 连接器版本——schema 漂移检测锚 + 可追溯（宪法 5） |
| `native_metadata` | 源原生元数据原样保留（作者/部门/表名/枚举原文） |
| `acl_tags` | **源权限随行**：映射为平台 ACL 标签，检索预过滤（主文档 §4.3）依赖；**无法映射的内容默认不可检索**（保守侧） |
| `cursor / occurred_at / occurred_at_trust / collected_at` | 游标 / 业务发生时间及其**可信度标记**（源时钟漂移或缺失时回退 collected_at 并打标，承接主文档 §8.2 `effective_date_known` 机制，防污染 `t_valid` 候选）/ 采集时间（= `t_txn`） |

幂等去重位置与窗口：`kb_connector_events` 按游标偏移去重（landing 缓冲层）+ 流水线侧按三元组 upsert 最新态（按 `source_sequence`）；**登记表 `kb_connector_events` 长期保留**（与 kb_facts 同生命周期，存最小快照：三元组 + 序号 + fingerprint + payload 哈希），T0 高频源单独容量预算。

### 3.2 生命周期与运行时

- **注册分级**：普通连接器走插件市场审核；**涉 REPL/binlog 等高敏凭据的连接器只允许内置/官方认证渠道**（第三方插件持全库可读凭据，出网白名单挡不住"合法读+外传"合谋）；
- **凭据**：平台密钥机制注入（环境变量，不落 server.json/库明文），连接器无凭据导出接口；
- **调度双通道**：批类连接器（T1~T3）走 `arq:queue:kb_batch` + 空闲闸门让路；**流式/T0 连接器走独立消费通道，不参与空闲闸门让路**（让路即破 ≤1min SLO），仅受源侧负载保险约束；
- **游标三纪律**（防最经典漏数据 bug）：① 水位读取固定回退重叠窗口（5~10 分钟，示例值），重复行由三元组幂等吸收——防源端时钟回拨；② 源侧历史回刷（backfill）走独立全量任务（复用 T3 快照 diff 通道），与增量游标隔离、完成后汇合；③ 游标丢失/损坏 → 降级为 T3 快照重建 + 重建期 SLA 顺延声明 + `last_error` 告警升级；
- **落地区**：MinIO `kb-landing`（90 天滚动，仅作缓冲）+ PG `kb_connector_events`（长期保留，追溯锚）。

## 4. 分场景接入设计

### 4.1 业务数据库（重点：ontology 方式接入 + 零侵入 + 资源效率统一）

**三段式管道**（每段独立故障域，业务库只与第一段有只读关系）：

```
业务库(只读) ──采集──▶ 落地中转区(MinIO kb-landing + PG kb_connector_events) ──映射/抽取──▶ 七步流水线 → kb_facts 权威层
   ▲                     完全解耦：断连不影响业务，追平不丢数据                     └─ 语义映射 = 主文档 §2.1 四步（映射 DSL 能力表见 §5.3）
   └── 平台绝不回写；回写唯一通道 = MCP action.invoke + 审批（账号/网络/代码三重分离）
```

**七重保险层**（"不能触及业务系统"的工程化落地）：

| 保险 | 措施 |
| ---- | ---- |
| 网络 | 业务库仅允许**中转区采集器**单向访问；平台其余组件网络不可达业务库 |
| 账号 | 只读账号 + **DBA 建只读视图白名单**（非裸表，不含敏感列）；**可访问集自检**（见下） |
| 数据 | 落地前字段白名单 + 敏感列脱敏；ACL 映射随信封 |
| 负载 | 优先只读副本；无副本则限速 + 错峰 + 熔断退避（指数退避+上限+抖动，初值示例；连续 N 次健康探测通过自动恢复，T2/T3 保守人工确认）；**暂停期 SLA 顺延——源侧保护优先** |
| 审计 | 采集全程留痕（何时/拉了什么/多少行/游标位置）进 audit_logs |
| 回写 | 连接器账号**永无写权限**（可访问集自检含"零写能力"校验）；回写只走 action.invoke 通道 |
| 分区 | 源所在安全分区前置评审（§2.0）；生产控制大区一律文件摆渡，不建数据库直连 |

**权限自检（可访问集 ⊆ 白名单）**：连接器每次 `discover()`/采集前用自身凭证实测当前可访问的表/视图集合，与准入白名单比对——出现超集（被扩权）或白名单对象不可达（被缩权/视图被改定义）即**断开采集 + 告警**。只用账号自身权限、跨数据库种类一致（DBA 侧 GRANTS 快照仅作月度冗余审计——PG 无枚举他人授权接口，v0.1 的"SHOW GRANTS diff"在 PG 不可行，已废弃）。

**schema 演进（源端 DDL 变更——静默变错比断连更危险）**：`discover()` 携带 `schema_fingerprint`（列名/类型哈希）；漂移即产生 `schema_changed` 事件 → **相关映射失效 → 派生事实自动转 `needs_review`**（与 §4.3 中台口径变更同款机制，泛化到一切结构化源）；准入清单评审含"列级映射覆盖检查"，漂移即触发复评。**任何结构化源接入前必须回答：源端加列/改类型/删列/改表名时，本链路发生什么？**

**同步分级 SLA**（资源与效率的统一——机制菜单按源能力与现实约束选）：

| 级 | 时效 | 机制 | 源系统前提 | 适用 | 成本 | 分期 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| T0 | ≤1 min | 事件推送 / CDC 流式 / 企业既有消息总线订阅 | **源可改造或已有总线**（老 ERP 不可改 → webhook 不可行，现实主路径=CDC/总线） | 高频高价值：工单状态、**停运事件**（⑥事件流） | CDC 通道+流式消费 | v1.5/v2 |
| T1 | ≤15 min | 增量轮询（水位 cursor） | 表有可靠 updated_at/序号列 | 中高频表 | 轮询任务 | v1.5 |
| T2 | 小时级 | 定时增量 | 同上 | 一般业务表 | 批任务（空闲闸门） | v1.5 |
| T3 | 日批 T+1 | 快照 diff（content_hash 全行比对，不依赖 updated_at；复用主文档 §8.6） | 只读快照可导出（**审批成本最低**） | 低频大表 / v1 起步 | 日批 | **v1** |

**CDC 前置条件清单（v2 启用前逐项 DBA 签字）**：① PG 需 `wal_level=logical`（源端配置变更+重启——**这本身构成"触及业务系统"，须单独评审**）；② MySQL 需 `REPLICATION SLAVE` 敏感权限；③ **replication slot 消费停滞会堆积 WAL 直至源库磁盘打满**——slot lag 监控 + `max_slot_wal_keep_size` 上限 + 弃槽重拍预案为硬性保险；④ 选型阶梯：源数量少时优先"源端逻辑复制 + 自研内嵌消费（pgoutput/binlog 客户端）"，**Debezium+Kafka 全家桶仅当 CDC 源超过阈值再上**（单机 Compose 加两个 JVM 服务级基建是重大决定）。v1 不上 CDC 的裁决维持不变。

**表清单准入评审**（不是全库接入）：逐表评审"知识价值密度 × 消费时效要求 × 映射到本体哪些对象/属性 × 被哪些查询消费"；**主键不可得时用准入评审确认的业务键组合做 external_id 锚；无业务键表一票否决不接入**；评审结论=版本化准入清单（含每源**属性级权威源矩阵**：attribute class → authoritative source_system，如技术属性→PMS、商业属性→营销，供 §5.4 使用）。

**源新鲜度水位与断供表现**（断连不拖累业务，也不得误导消费端）：`kb_connector_cursors` 记每源最近成功采集时间；检索答案/前端按源展示**数据截止时间**；超过源级 SLA 的 N 倍（示例值/待实测）→ 置 stale 告警 + 答案免责标注（"该源数据截至 X 时点"）——防止用户拿过期停电范围去抢修。

### 4.2 文件管理系统（DMS/网盘/Wiki/合同系统）

- 增量发现：目录扫描（mtime+内容哈希）或源 webhook → fetch 落 Raw → metadata（作者/部门/ACL）随信封 → 七步流水线；
- 与主文档 §8.0 同源检测天然衔接（SHA-256/身份键/SimHash）；目录语义（`/制度/`、`/标准/`）作 `kb_collections` 归类与抽取模板路由提示，仅提示不作门禁；
- Wiki 页面更新=modified 事件 → 版本链（身份键=space+page_id）；合同系统按合同号身份键（主文档 §2.1 合同条款切分已有承接）。

### 4.3 数据中台（数仓/指标平台）

- 接入重点不是行数据而是**指标口径**：指标定义/口径/维度 = 规则类知识（`risk_flag=true`，100% 人工终审，宪法 3）；
- 模式：T+1/API 拉取指标元数据层 → 主文档 §2.1 映射通道（指标→本体规则对象）；
- **口径变更事件 → 相关事实自动转 `needs_review`**（防"指标悄悄变义"；此机制已泛化为 §4.1 schema 演进通用机制）。

### 4.4 邮件系统（合规红线）

- **默认只收显式投递**：① 平台投递地址（转发/抄送=人主动授权）；② 用户上传 `.eml`；③ 共享邮箱+标签规则。**个人邮箱绝不默认接入**；
- **共享邮箱接入前置三条件**（防"把我们部门邮箱全接进来"冲垮防线）：① 接入范围准入评审（同 §4.1 表清单同款流程）；② 书面审批含**保密部门会签**；③ 正文敏感字段（身份证/手机号/账号）落地前脱敏。**明文：全量归档 ≠ 全量入库——归档留在邮件侧，入库范围另行准入**；
- 正文+附件拆分分流；ACL = 发件人/收件方部门映射（见 §5.5 ACL 映射为一等工程项）。

### 4.5 爬虫系统（外部源）

- 产出**不直接入库**：落准入暂存区 → 可信度分级（白名单自动进流水线但标 `provenance=external`；未知来源强制人工审核）；
- 信封必带 `source_url + fetched_at + fetcher_version`；防投毒：语料投毒校验（主文档 §8.5 P2 项升格为外部源强制门禁）；
- 运行形态：**长驻调度驻插件守护进程，抓取执行落一次性沙箱会话**（不可信出口默认拒绝——不把常驻进程塞进会话式沙箱，也不让守护进程直接出网）。

### 4.6 日志/监控/告警/生产事件流

- 三档分流（§2.1 表）：量测流不入库只存指针；**事件流（停运/复电/遥信变位）经 §4.1 通道成事实**；蒸馏知识走候选审核；
- 大区事件源按 §2.0 红线走文件摆渡（E 语言/告警导出），摆渡节拍决定其 SLA 上限（T2~T3 起步）。

## 5. 跨系统语义消歧（FDE 痛点：同一句话不同系统含义不同）

**问题实例（电力场景）**："工单"在营销=用电业务工单、PMS=检修停电工单、ERP=采购工单；"已关闭"三系统三种语义；"配变容量"营销记契约值、PMS 记铭牌值——同一个词、同一台设备，不同系统不同含义。

### 5.1 跨系统差异的三类情形与各自正解（v0.2 修正——出处归因 ≠ 适用域）

v0.1 曾把"source_system 不相交 ⇒ 自动 T3 共存"当机制，这是**范畴错误**：既有 scope 四键（temporal/region/…）都是**适用域限定语**（事实在其 scope 内成立），而 source_system 是**出处归因**（谁说的）——现实世界不因源系统分叉，一刀切"都有效"会把 (c) 类数据质量问题永久掩盖。跨系统同主谓异值实为三类：

| 情形 | 例子 | 正解 | 是否进冲突分诊 |
| ---- | ---- | ---- | ---- |
| (a) 同词异义 | "工单"三系统三物 | **术语语境层解为不同主语 IRI**（§5.2）——主语不同，分诊永不触发 | 否 |
| (b) 同实体同谓词、口径不同 | 契约容量 vs 铭牌容量都映射到 `ratedCapacity` | **拆谓词**（`contractCapacity` vs `nameplateCapacity`）——映射评审修正 | 不应触发（映射错误即修） |
| (c) 同实体同谓词、一方录入错误 | 同一台配变营销 400kVA、PMS 500kVA | **数据质量问题**——T2 冲突工单裁决，绝不共存 | 是 |

**谓词级声明制（`systemRelative`）**：TBox 属性定义增加 `systemRelative` 标记（值语义本就是各系统本地口径的属性，如 `localStatus`、`localCategory`）；**仅带此标记的谓词**，跨系统同主谓异值按分诊固定顺序自动判 T3 共存；未标记谓词跨系统异值 → T2 工单（主文档 v1 全人工裁决），工单裁决项增设两项：「判定映射缺陷 → 退映射评审拆谓词」「判定数据质量缺陷 → 生成 DQ 告警记录（**只读报告通道**，不回写业务库——公理 2）」。判定基础 = TBox 声明 + 规则引擎（确定性），符合推理分级宪法 2。授权链条：scope 枚举扩展 + span 豁免 + 行事件链已在**主文档 §8.1 同步增补**（本文引用之）。

### 5.2 语境感知术语表

- 绑定结构：`label + source_system → IRI`（"工单"@营销 → `mkt.BusinessOrder`；"工单"@PMS → `pms.MaintenanceOrder`）；
- **唯一事实源**：结构化源的该绑定由已人审的映射规则**派生生成**（投影），术语表自身只承接非结构化通道的澄清回流（L3→L4 既有通道）——避免与映射规则双头维护漂移；
- 检索衔接：`knowledge.search` 增 `source_context: {source_system?}` 参数（Agent 会话/接入视图携带，网关注入不可篡改，同 tenant_scope 模式）；无上下文时查询词命中多个 source_system 绑定 → **分组返回**（每组携 `{bound_iri, source_system}` 与组内答案）——分组形态需回写主文档 §5 返回 schema（§10 待办）；术语对齐三步的引用锚 = 主文档 §2.4，查询期同义扩展 = 主文档 §4.3 #3。

### 5.3 语义映射器（结构化源 → 本体；主文档 §2.1 四步的泛化）

映射 DSL 能力表（v1 范围逐项写死）：

| 能力 | 例 | v1 |
| ---- | ---- | ---- |
| 列→类/谓词绑定 | `PMS_WORK_ORDER.STATUS → wo:localStatus` | ✅ |
| PK→IRI 生成模板 | `pms:WO:{wo_id}` | ✅ |
| 行过滤谓词 | 只接 `dept_cd IN (...)` | ✅ |
| 常量注入 | 补 `source_system=PMS` | ✅ |
| FK join 组合嵌套对象 | 工单→设备对象嵌套 | ✅ |
| 枚举码表翻译 | 状态码 03→"复电归档"（码表注册为映射资产） | ✅ |
| 单位换算 | kV→V（声明式，QUDT 风格单位语义） | ✅ |

### 5.4 跨系统实体解析（xref:sameAs）

- **键域区分**（防"设备编码"幻觉）：自动绑定仅限**共享键域**（双方引用同一主数据键，如统一社会信用代码；键域注册表随准入评审维护）；**异键域**（营销设备码 vs PMS 设备码是两套编码体系）禁止自动绑定——属性相似度（名称+地址+容量）预排序 + 高价值实体类（配变）优先分批人工裁决（避免百万级设备淹没终审队列——主文档 §7.1 同款批判）；
- **合并时刻语义**（防"合并=批量制造无人知晓的共存矛盾"）：sameAs 绑定激活前，对两实体重叠谓词执行一次**分诊预演**——`systemRelative` 谓词自动共存；真值谓词进 DQ 批量工单；全部处置完毕才激活 sameAs 边；
- **属性级权威源矩阵**（§4.1 准入评审登记）：检索默认呈现权威源值，非权威源值以"他源报告 X"标注伴随（最小 golden record）；
- **可逆与规范 IRI**：sameAs 为带 evidence 的可逆绑定（合并 diff 留痕，可拆分重放——主文档 §8.5 既有纪律）；每实体类指定 canonical IRI 归属（设备类以 PMS IRI 为规范 IRI）；
- **实体级 ACL**：合并实体各源 acl_tags 不同时，实体节点与图遍历枢纽的 ACL 取**源并集最严者**（防经图谱跳板读到高敏源实体名，衔接主文档 §4.3）。

### 5.5 FDE 部署工具包与"同词异义清单"

**清单生成算法（三步）**：① 候选对生成：label 归一化精确命中 + 列名/注释嵌入相似度（阈值随 PoC ④ 标定）；② 语义差异信号：同名列**值域画像分歧**——枚举列值集 Jaccard、类型分歧（string vs numeric）、FK 指向分歧；同名且画像显著分歧 → "高疑似异义"，同名画像一致 → "疑似同义待合并"；③ 聚类汇聚为本体对象/谓词候选 + 逐源绑定建议 → 清单工件版本化，作为映射 changeset 的评审输入附件。

**ACL 源权限主数据映射表**：工单库部门码、DMS 目录 ACL、邮件通讯录是三套组织体系，对齐是按周计的人工活——升格为**一等知识资产**（人工维护+版本化+走变更评审）；v1 = 手工映射表仅覆盖单源 PoC；默认拒绝语义（§3.1）兜底。

**工具包 v1 最小集 = 离线可用四件**（账号没批下来时第一周就能干活——在线扫描只是增强项）：① DDL/数据字典导入器（吃建表 SQL、数据字典 Excel、报表样例）；② 同词异义清单 Excel 模板；③ 映射规则 YAML 手填模板；④ 清单报告生成器。

## 6. 动态知识：从"答案"到"下一步"（OB2 闭环的知识侧）

### 6.1 知识活性——资源效率统一的反馈环

- `kb_facts`/实体带 usage 统计：`search_hits` / `action_refs` / `last_accessed`（写入时即有，零成本埋点，v1 即做）；
- 用途：SLA 升降级评审输入（§4.1，高频使用的知识 deserve 更高级别）；抽取/映射优先级；零引用知识 → nightly lint 清理候选；
- 隐私边界：只记计数与时间戳，不记"谁查了什么"的内容级日志（后者在审计域，权限隔离）。

### 6.2 `knowledge.next_actions`——推理下一步（与推理分级一致，宪法 2）

```
输入：当前知识状态（kb_facts 查询/事件流事实）+ 本体行动类 + 规则库
确定性推理（高频，毫秒级）：规则物化（SPARQL CONSTRUCT）命中"条件→建议行动"
输出：行动建议清单，每条 = { 触发规则 IRI, 证据链(kb_facts 引用), 建议动作(MCP 工具引用), 审批级别, must_suggest 标记 }
LLM 介入（低频）：仅呈现顺序排序与自然语言解释
```

**可实现性衔接件**（规则三元组 → 结构化建议的三段桥）：① 规则后件 CONSTRUCT **行动类实例**（OB2 行为层）；② 行动类携带 `hasToolBinding → MCP 工具 IRI` + `requiresApprovalLevel` + 参数模板（规则命中变量按模板填参）——三者均属 TBox，与"规则类 100% 人工终审"（底线 3）自洽，衔接本体核心 §2.2 行动类既有定义；③ **LLM 硬约束**：排序仅影响呈现顺序，不得增删候选、不得改写工具绑定与审批级别，`must_suggest` 规则命中固定置顶不可过滤，解释仅可引用该规则证明链内证据；④ **行动去重**：建议登记表按 trigger 指纹（规则 IRI + 证据事实 IRI 集合哈希）查重，防 T+1 滞留下反复建议同一事件派单。

**电力示例**：知识状态"配变 T-102 停运 42min × 影响 137 户"（⑥事件流入库的事实）+ 规则 R-017"配变停运>30min 且影响>100 户 → 建议启动应急抢修" → `next_actions` 返回"派发应急抢修工单（`action.invoke @工单系统.createEmergencyWO`，team 确认）+ 证据链 + R-017"。行动结果经 action_service 回写 → 事实更新 → 下次推理更新——**闭环**。

## 8. 与其他服务的关系

- **MCP 网关**：`action.invoke` 是平台唯一业务回写通道（与连接器读通道物理分离）；外部系统可经 MCP inbound 反向推送事件（默认 untrusted 审核）；

- **Sandbox**：爬虫**抓取执行**落一次性沙箱会话，长驻调度驻插件守护进程（§4.5）；
- **记忆服务**：连接器事件不属于 L1~L3 记忆；Agent 会话中的字段澄清（"这个字段在 ERP 其实指 X"）经 L3→L4 通道反哺术语语境表（主文档 §4.4 边界不变）。
